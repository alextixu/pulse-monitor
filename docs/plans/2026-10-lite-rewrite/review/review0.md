# Review: review0

The fan-safety core survives the split because the pieces that matter (LibreHardwareMonitorService's single lock + ThrowIfDisposed-under-lock + 5 s TryEnter Dispose, FanModeController's internal gate and Stop flag, FanRecoveryJournal's same-boot orphan adoption) are moved verbatim and are thread-agnostic, and the scheduled task's RestartOnFailure composes correctly with the journal. The design is NOT shippable as written on the crash path, though: section 4 claims the ordered, async, IPC-and-store-flushing shutdown is "identical to today" for unhandled exceptions and ProcessExit, but today's abnormal path is a two-call synchronous restore (App.axaml.cs:92-106) with no dependency on any scheduler thread; running the full chain from a crash handler can leave fans held. Top three concerns: (1) the crash/ProcessExit path must stay a minimal synchronous `Stop(); hardware.Dispose()` with no Post to the engine thread; (2) FanFirstSight persistence across reboots turns transient first-sight pollution (orphans parked at 100 % by Dispose, hardware swaps) into permanent pump/hidden misclassification, so it must be boot-scoped and skip fans Pulse itself was driving; (3) the engine threading model is ambiguous about where the blocking LHM call runs, and SetFan/UpdateSettings over IPC are an unguarded write surface racing FanModeController. Also missing: WM_QUERYENDSESSION/WM_ENDSESSION handling in the new TrayWindow (the only place that can stop fans being orphaned at logoff), joining the concurrent WMI disk query before the first Accept (HDD spin-up), and keeping demo-mode AgentCore away from the real state.json.

## blocker (1)
### Crash/ProcessExit path is not 'identical to today' and can leave fans held
**Detail:** Design §4 lists one shutdown order for clean exit, --quit, unhandled exception and ProcessExit: tray removed → IPC AgentExiting + close → FanModeService.StopApplying → MonitoringService stop → TelemetryLogger flush → IHardwareMonitor.Dispose → RGB → OpenRGB kill → StateStore flush → SingleInstance release. Today the abnormal path is only `_fanModes?.StopApplying(); hardware.Dispose();` executed synchronously on whatever thread raised the event (src/Pulse.App/App.axaml.cs:92-106, src/Pulse.App/Program.cs:75-83), with no dispatcher hop and no I/O before the fan restore. In the new design every step before `IHardwareMonitor.Dispose` is either an engine-thread Post (FanModeService/MonitoringService state is engine-thread-only per §3) or blocking I/O (pipe write to a UI that may be dead, telemetry flush). When the engine thread itself faulted, is blocked inside LHM, or the exception came from a WndProc/thread-pool thread, a Post never runs and an awaited step never completes; the process then exits with fans at Pulse's duty and the journal still populated. The restarted agent will adopt them as orphans (stand-in curve), but the whole point of the hook is that a crash that reaches managed code hands fans back cleanly so the restart starts with BIOS curves.

**Fix:** Keep two paths. Clean path: the ordered list, but move `FanModeController.Stop()` + `IHardwareMonitor.Dispose()` before any IPC/telemetry/RGB step. Abnormal path (AppDomain.UnhandledException IsTerminating, ProcessExit): a static `RestoreFansOnAbnormalExit` that only does `controller.Stop(); hardware.Dispose();` synchronously on the calling thread, touching no Channel/Post/pipe/file other than the journal that Dispose already writes; make it idempotent via a flag set at the end of the clean path (today's `_hardware = null`, App.axaml.cs:232). State this explicitly in §4 and pin it with a test on a fake IHardwareMonitor that asserts Dispose is reached when the engine thread is deadlocked.

## major (9)
### FanFirstSight persisted across reboots makes transient misclassification permanent
**Detail:** §8 seeds FanPresenceTracker from state.json with no boot scope or capture guard. FanGroupPolicy.LooksLikePumpDuty (src/Pulse.Core/FanControl/FanGroupPolicy.cs:53-54) marks a fan PumpLike when first seen at ≥2800 RPM or ≥95 % duty with ≥1800 RPM; Evaluate (:60-68) then excludes it from Quiet/Synced. Today the first sight is re-sampled every process start, so a bad sample heals on restart/reboot. Concrete failure: an orphaned board fan is parked at OrphanExitPercent=100 by Dispose (src/Pulse.Hardware/LibreHardwareMonitorService.cs:211-216); the next agent start in the same boot records FirstSight{Percent 100, Rpm ~2000} → PumpLike → excluded; the design now writes that into state.json, and after the reboot (fan back on the BIOS curve, no longer orphaned) it is still 'pump-like' forever until the user manually toggles 納入群組控制. Second failure: the key is the header id (/lpc/nct6798d/0/fan/N), not the fan; swapping a case fan for an AIO pump on that header keeps the old 'normal fan' first sight, so Quiet drives a pump at 35 %. Third: EverSpun is sticky; a header whose fan was removed stays Visible forever, defeating the hidden-header feature and letting Quiet/Synced write to an empty header. The live rig already needed FanGroupIncludedIds=[fan/1] to override this heuristic (measure.md persistedState), so misfires are real.

**Fix:** Store FanFirstSight with the same boot identity the journal uses (FanRecoveryJournal.CurrentBootTime, 2 min tolerance, src/Pulse.Hardware/FanRecoveryJournal.cs:22-23,37,48) and discard it on a new boot — the goal is stability across agent restarts within a boot, not across reboots where the BIOS state is ground truth and re-sampling is free. Never record a first sight for a fan whose id is in the journal's manual list, in OrphanedFanIds, or has IsManual=true at capture time; leave it unseeded so the first clean sample seeds it. Persist Samples (or seed Samples=0) so a seeded header still gets the 3-sample grace. Add this to the §11 contracts and to the Pulse.Core.Tests fan-safety invariants.

### Engine thread must never block on LHM, and ShutdownAsync must not depend on it
**Detail:** §3 says blocking hardware calls run on the thread pool, then says 'the 1 Hz hardware loop calls LHM directly from its own loop task (no Task.Run inside Task.Run)'. It is not stated whether that loop task is the engine thread. computer.Accept runs under _lhmLock and takes tens of ms normally and seconds when a driver stalls (today's HardwareTimeout is 10 s, src/Pulse.App/Services/MonitoringService.cs:56; a hung Accept never returns). If the loop or FanModeController.UpdateAsync (which awaits SetFanAsync → Task.Run + lock, LibreHardwareMonitorService.cs:150-191) is awaited on the engine thread, every Post — IPC Quit, SetFan replies, the §4 shutdown steps — queues behind it, and the --quit waiter times out at 15 s (Program.cs:13). Today FanModeService runs UpdateAsync fire-and-forget on the pool with a single pending-request slot (FanModeService.cs:124-176) and the UI thread is never blocked. Separately, if the EngineScheduler's drain loop does not catch per-action exceptions, one throwing handler (e.g. LightingMemory write) terminates the dedicated thread → process crash → RestartOnFailure loop (3×) and then no agent at all.

**Fix:** Specify: the 1 Hz loop runs on a pool task or its own 'Pulse.Hardware' thread; it calls LHM synchronously there and Posts the snapshot to the engine thread; FanModeController.UpdateAsync keeps today's single-flight latest-wins drain on the pool and Posts the FanModeResult back. ShutdownAsync runs on the caller's thread using Stop flags and bounded waits (WaitIdle 3 s, loops 2 s) and must not require an engine Post to reach IHardwareMonitor.Dispose. The drain loop wraps each Action in try/catch + LogError. Add a 'last successful poll > 30 s → HardwareMonitorState.Failed' watchdog to replace the removed 10 s timeout so FanModeResult goes Unavailable instead of silently freezing.

### SetFan over IPC bypasses FanModeController ownership and the orphan guard
**Detail:** §4/§5 route `SetFan{FanId, Percent?}` straight to IHardwareMonitor.SetFanAsync. Today the only gate is UI-side: FansViewModel disables manual controls outside 個別 mode and for StandIn fans (ui.md mustPreserve; FansViewModel.cs:365-373) and calls `_hardware.SetFanAsync` from Task.Run (FansViewModel.cs:513). Over a pipe the UI can be stale (mode just changed), slow, or a dev tool. Race 1: user drags a slider while FanMode flips to Quiet; the controller's mode-switch hand-back (FanModeController.cs:174-194) runs, then the late manual write lands; the fan is now manual but not in `_controlled`, so the controller never hands it back until the *next* mode switch (it only hands back `fan.IsManual` fans at a switch, :185-188). Race 2: SetFan with a percent for an orphaned id in 個別 mode — StandIn only re-writes when the target rises or moves ≥3 % after 4 s (:225-236) and never reads back fan.Percent, so a manual 20 % silently overrides the stand-in curve on a fan whose BIOS curve is gone. SetFan(null) on an orphan is safe (LibreHardwareMonitorService.cs:164-172) but SetFan(percent) is not.

**Fix:** AgentCore.SetFanAsync executes on the engine thread and validates against current state before touching hardware: reject (Reply.Error, no exception) when Settings.FanMode != Individual, when the id is in HardwareStatus.OrphanedFanIds, when FanModeResult shows StandIn/NotControllable, or when ControlAvailable is false. Re-run the controller evaluation right after a successful manual write so IsManual/_controlled stay consistent. Document that the UI guard is advisory and the agent guard is the contract (§11).

### UpdateSettings replaces the whole AppSettings from a stale UI copy (lost update on fan settings)
**Detail:** §6: 'SettingsViewModel mutates that copy and calls client.UpdateSettings(copy, name)'. The agent also mutates settings itself via SetFanMode/SetSyncedPercent/SetFanMembership (today FanModeService.cs:73-99 mutates FanMode, SyncedFanPercent, FanGroupExcludedIds/IncludedIds in place) and broadcasts. If the Settings tab's copy was taken before such a broadcast (or the broadcast is in flight) and the user changes an unrelated field (theme, OpenRGB port), the whole-object replace reverts FanMode / membership lists to stale values. FanModeController sees `_lastMode != settings.Mode` and executes a full hand-back/take cycle (FanModeController.cs:174-194); for orphans hand-back is skipped so they stay on the stand-in, but non-orphans flip to BIOS and back, and a user's 納入群組控制 toggle can vanish. Today this cannot happen because there is exactly one shared mutable AppSettings instance (App.axaml.cs:255).

**Fix:** Make UpdateSettings a patch: the agent applies only the property named by `changed` (or send `UpdateSetting{Name, ValueJson}` as ui.md rewriteNeeded already proposes); keep the fan-specific commands as the only writers of FanMode/SyncedFanPercent/FanGroupExcludedIds/FanGroupIncludedIds. If whole-object stays, add a monotonically increasing Settings.Version to the broadcast and have the agent reject updates whose base version is not current (Reply.Error → UI re-reads).

### WMI disk query concurrent with Computer.Open can let the first Accept query the HDD
**Detail:** §2/§9 move DiskMediaTypes.Read to run concurrently with Computer.Open. Today `_disks` is read and the UpdateVisitor's skip predicate (`DiskMediaTypes.Find(drive.Name, disks)?.IsHardDisk == true`) is built *before* Open and the first Accept (LibreHardwareMonitorService.cs:371-377,386); the predicate captures the list by value. If the first `computer.Accept(_updateVisitor)` runs before the WMI result arrives, every drive passes ShouldUpdateStorage (UpdateVisitor.cs:48-61) and LHM issues a SMART read to the rotating disk — the exact spin-up the 'storage safety' invariant forbids (hardware.md mustPreserve). The existing failure fallback already does the wrong thing ('all drives will be polled', DiskMediaTypes.cs:135), so a timeout on the concurrent path would silently poll the HDD every 10 s for the process lifetime.

**Fix:** Start the WMI query on a pool (MTA) thread — never on the STA tray thread — and `Wait` on it (bounded, e.g. 5 s) immediately before the first Accept; make the visitor's predicate read a volatile `_disks` field so a late result still applies. On timeout/failure, skip ALL storage updates (treat every drive as unknown → not polled, StorageInfo values null) until the metadata is available, instead of polling all; log once. Add a test with a fake predicate asserting no storage Update before disks are known.

### No WM_QUERYENDSESSION/WM_ENDSESSION handling: fans are orphaned at every logoff
**Detail:** The agent is a WinExe with a hidden top-level window and its own GetMessage loop (§7). At user logoff/shutdown Windows sends WM_QUERYENDSESSION/WM_ENDSESSION to that window and then terminates the process; AppDomain.ProcessExit does not run for a GUI process on this path (the console control handler route does not apply to a WinExe). The spike WndProc handles WM_COMMAND/WM_CLOSE/WM_DESTROY only (docs/plans/2026-10-lite-rewrite/spikes/tray/Program.cs:155-190) and the design is silent. With the live settings (FanMode=Quiet, measure.md persistedState) fans are always held, so every logoff-without-reboot leaves board fans at the Quiet duty; the next logon's agent reads the same-boot journal, adopts them as orphans, shows 「Pulse 上次未正常結束…」and runs the stand-in curve until reboot. Today's Avalonia process has the same gap, so this is not a regression, but the new TrayWindow is the first component that can fix it and the design should not re-create the hole knowingly.

**Fix:** In TrayWindow.WndProc: on WM_QUERYENDSESSION call ShutdownBlockReasonCreate(hwnd, "正在把風扇交回 BIOS…") and kick off the synchronous abnormal-exit restore (`controller.Stop(); hardware.Dispose()`, bounded by Dispose's 5 s TryEnter) on a pool thread, return TRUE; on WM_ENDSESSION(wParam=TRUE) join that restore (≤5 s), ShutdownBlockReasonDestroy, then let the process die. Add it to §4 as a third shutdown trigger and to §11.

### Demo-mode AgentCore in the UI process writes the user's real state.json
**Detail:** §4 composition: 'Demo mode (UI process): the same AgentCore with Demo providers and a DemoSettingsStore (never writes) and telemetry off'. StateStore (§8) is owned by AgentCore and is not mentioned. DemoBatteryProvider devices, DemoRgbController intents (every Demo RGB command succeeds, src/Pulse.App/Demo/DemoRgbController.cs:94-190, so LightingMemory records them), DemoHardwareMonitor fan ids `demo:fan:*` (DemoHardwareMonitor.cs:34-42) and its low-battery notified set would be merged into %LOCALAPPDATA%\Pulse\state.json. The real agent then publishes the demo batteries as remembered disconnected devices with 「上次 HH:mm」 for 30 days and seeds FanPresenceTracker with demo keys. Today demo mode is isolated by DemoSettingsStore + no TelemetryLogger (App.axaml.cs:157,246-265); the new memory feature breaks that isolation.

**Fix:** Give the in-proc demo AgentCore a NullStateStore (load empty, never write), a null journal path for any IHardwareMonitor it hosts, and assert in Pulse.Core.Tests that `--demo`/`--screenshot` runs leave state.json, fan-recovery.json, rgb-defaults.json and telemetry untouched. Mention 'StateStore' alongside 'DemoSettingsStore' in §4.

### 'UI never disposes or restores fans' is a convention, not a structural guarantee
**Detail:** §2 says Pulse.App 'loses every hardware/HID/RGB reference', yet it references Pulse.Engine for InProcPulseClient, and Pulse.Engine as described hosts OpenRgbServerLauncher.Dispose in the shutdown order (§4) and composes LibreHardwareMonitorService/IRgbController types — if Pulse.Engine references Pulse.Hardware/Pulse.Rgb, the UI exe transitively carries LibreHardwareMonitorLib, HidSharp and OpenRGB.NET and can open the driver; a future 'quick fix' that news up LibreHardwareMonitorService in the UI's demo path compiles. The UI's Program.cs today also installs the fan-restore ProcessExit/UnhandledException hooks (Program.cs:75-83); the design does not say they are removed from Pulse.UI.

**Fix:** Pulse.Engine may reference only Pulse.Core (+ logging abstractions); OpenRgbServerLauncher, LibreHardwareMonitorService, providers are injected by Pulse.Agent behind Core interfaces (add `IRgbServerLauncher : IDisposable` to Pulse.Core). Add a build-time guard (a test that walks Pulse.App's transitive references and fails on Pulse.Hardware/Pulse.Rgb/LibreHardwareMonitorLib/HidSharp, or `dotnet list package --include-transitive` in publish.ps1). State in §6 that Pulse.UI's Program installs no fan hooks.

### ShutdownAsync budget vs the 15 s --quit waiter: Dispose can be cut off with fans held
**Detail:** Clean-path worst case today: FanModeService WaitIdle 3 s (FanModeService.cs:20) + MonitoringService loops 2 s (MonitoringService.cs:723) + TelemetryLogger 2 s (TelemetryLogger.cs:238) + IHardwareMonitor.Dispose TryEnter 5 s (LibreHardwareMonitorService.cs:30) + per-control writes; the design adds 'wait ≤3 s for the UI to exit' (§10) in front of it, totalling ≈15 s — exactly Program.cs:13 QuitTimeout. §4 introduces `ShutdownAsync(TimeSpan budget)` but does not say what happens when the budget expires; if it falls through to exit 0 while Dispose is mid-restore, `_touchedControls` is cleared and the journal rewritten only when every restore succeeded (:228-232), so a half-finished restore leaves fans held with a journal that the next start treats as orphans (stand-in until reboot) — and the user's update script (`--quit` → publish → schtasks /run) proceeds after a timeout return code 1 and replaces the DLLs under a still-running agent.

**Fix:** IHardwareMonitor.Dispose is never subject to the budget; order it immediately after Stop/StopApplying (before UI-exit wait, IPC close, telemetry flush, RGB/OpenRGB teardown) so it completes within ~8 s worst case. Run the UI-exit wait concurrently with the hardware restore rather than before it. Keep Program's QuitTimeout ≥ sum of the remaining bounded waits + 5 s, or raise it to 20 s, and document the arithmetic in §4.

## minor (6)
### Shutdown order puts the IPC 'AgentExiting' write before StopApplying
**Detail:** §4: 'tray removed → IPC sends AgentExiting and closes → FanModeService.StopApplying'. StopApplying is a flag set (FanModeService.cs:179-183) and is the first thing today's abnormal path does; a pipe write to a UI that stopped reading (hung Avalonia, frozen debugger) can block or wait for a timeout before fan writes are stopped.

**Fix:** Set the controller Stop flag first in every path, then tray/IPC; bound the AgentExiting send with a short timeout (e.g. 500 ms).

### WndProc exceptions must be contractually swallowed (UnmanagedCallersOnly → FailFast skips the fan hooks)
**Detail:** The spike's WndProc is `[UnmanagedCallersOnly]` (spikes/tray/Program.cs:154) and correctly wraps its body in try/catch (:157-187). An exception escaping an UnmanagedCallersOnly callback is a runtime FailFast: AppDomain.UnhandledException and ProcessExit are NOT raised, so no fan restore. GdiTrayIconRenderer, TrackPopupMenuEx handling and the 400 ms coalesced update all run inside this callback in the design (§7); the design does not carry the try/catch over as a requirement.

**Fix:** Add to §7/§11: every UnmanagedCallersOnly entry point (WndProc, timer callbacks posted as custom messages) catches all exceptions, logs, and returns DefWindowProc; icon rendering failures fall back to the static glyph as TrayIconRenderer does today (services.md mustPreserve).

### Debounced settings save off the engine thread can serialise lists while they are being mutated
**Detail:** §4: UpdateSettings 'saved (500 ms debounce)'. Today the debounce is a DispatcherTimer so SaveNow runs on the same thread that mutates FanGroupExcludedIds/IncludedIds (SettingsService.cs:31,65-81; FanModeService.cs:92-96 does Remove/Add on those Lists). With a System.Threading.Timer the save runs on a pool thread; System.Text.Json enumerating a List<string> that the engine thread is mutating throws InvalidOperationException → save fails (logged only) → the user's fan-group choice is lost if the agent later crashes.

**Fix:** Have the timer callback Post to the engine thread, clone/serialise AppSettings there (AppSettings.Clone plus list copies), and do the file write off-thread with the serialised bytes.

### Memory-group throttle must not skip the first Accept, or telemetry columns and DIMM temperatures become run-dependent
**Detail:** §9 updates Memory hardware every 5 s via the visitor. TelemetryLogger fixes columns from the 4th sample (TelemetryLogger.cs:19,98-107) and SnapshotBuilder only emits a temperature when the sensor has a value (SnapshotBuilder.cs:144-146). If the throttle counts from process start rather than from the last update, the Memory root may have null sensors in samples 1-4 → '記憶體 DIMM #0/#2' columns missing in that file and present in the next, breaking the 'telemetry CSV columns' contract in §11.

**Fix:** Implement the throttle as 'skip if updated < 5 s ago' with no entry for never-updated hardware, mirroring the storage throttle (UpdateVisitor.cs:57-60), so the init Accept and the first loop Accept always update Memory.

### Controller/PSU opt-out drops journal leftovers for those fans with no stand-in and no notice
**Detail:** With `ProbeUsbCoolers=false` the Controller/PSU LHM groups are not opened. If the previous (current-build) Pulse was killed while holding a Corsair/Aqua Computer/NZXT fan, RecoverFromPreviousSessionLocked finds no binding for its id and, being elevated, logs a warning and drops it (LibreHardwareMonitorService.cs:274-283): the fan stays at the stuck duty, is not orphan-tracked, and the UI shows nothing. Not reproducible on the rig (no such devices) but it is a one-time regression for every user upgrading with those fans held.

**Fix:** When journal leftovers reference ids that are not visible and the optional groups are disabled, either enable Controller/PSU for that session and re-run recovery, or carry the entries over (as the non-elevated path does, :276-281) and surface them in RecoveryNotice.

### §8 still calls the pump rule 'uncommitted'
**Detail:** The 'only named pumps run flat out' change is committed as af3e117 (git log on FanModeController.cs; working tree clean). hardware.md/services.md also describe it as uncommitted.

**Fix:** Update §8 and the analysis maps to say the rule is committed; the Pulse.Core.Tests golden test for StandIn should assert FanExclusion.PumpName only.

- The 10 s hardware snapshot timeout and 'returning the previous snapshot' warning (MonitoringService.cs:56,394-396,606-609): §3 calls LHM directly from the loop, which removes the outer timeout; nothing replaces it, so a stalled driver freezes fan evaluation silently instead of logging and marking the monitor unhealthy.

- Fans tab hidden-header decisions come from the live FanPresenceTracker synchronously with each snapshot today (FansViewModel.cs:215-219 via FanModes.Presence); §5 moves them into FanModeResult.Presence, which is produced one asynchronous evaluation later and not at all when snapshot.Fans.Count == 0, so the hidden count can lag the fan cards by a tick.

## confirmedSound
- Moving LibreHardwareMonitorService, FanModeController, FanGroupPolicy, QuietFanCurve and FanRecoveryJournal verbatim is safe: none references Avalonia/Dispatcher (verified csproj references and usings), LHM access is serialised by `_lhmLock` with ThrowIfDisposed re-checked under the lock (LibreHardwareMonitorService.cs:152-156), and Dispose restores fans with or without the lock after 5 s (:198-240), so the hand-back does not depend on which thread or process part calls it.
- FanModeController is internally serialised (`_gate`, FanModeController.cs:91,137,389) and checks `_stopped` between every write (:148,344,363); FanPresenceTracker's single-thread contract (FanGroupPolicy.cs:73-74) is satisfied by doing Observe/Capture on the engine thread exactly as it is done on the UI thread today.
- Routing every fan write (per-fan manual, mode writes, hand-backs) through the agent keeps all writes behind `_lhmLock` and the journal, which hardware.md rewriteNeeded requires; the UI holding no IHardwareMonitor removes the second writer that exists today (FansViewModel.cs:513).
- Scheduled-task RestartOnFailure (3×/1 min, tools/install-pulse.ps1:49-50) composes correctly with the journal: a crash that reaches UnhandledException restores fans and deletes the journal (Dispose :228-232 → Write deletes when empty, FanRecoveryJournal.cs:64-67), so the restarted agent starts clean; a hard kill leaves the journal with BootTime and the restarted agent adopts the orphans within a minute (:260-314) — today nothing restarts, so this is strictly better. `--quit`/tray 結束 exit 0 and are not restarted, as the task's failure semantics require (platform.md mustPreserve).
- Two processes make a UI-side exception (view binding, Avalonia platform) incapable of killing the fan controller, which today takes the whole process (and fan control) down.
- Keeping OrphanExitPercent=100 on shutdown, never handing orphans back in any mode, the StandIn curve points and the SetDefault semantics unchanged (§11) is correct; nothing in the split requires touching them, and the orphan list remains same-boot scoped via the journal.
- A killed agent cannot leave the bundled OpenRGB behind: the kill-on-close job object (OpenRgbServerLauncher.cs:132,167-197) survives unchanged in the agent, and the UI never launches OpenRGB.
- Single-instance protocol unchanged in the agent (Global\Pulse.SingleInstance / ShowPopover / Quit with Authenticated Users Synchronize|Modify ACLs, SingleInstance.cs:186-213) so an unelevated `Pulse.exe --quit` still reaches the elevated task-launched agent and waits for a complete clean shutdown before the mutex is released (Program.cs:356-359).

## questionsForUser
