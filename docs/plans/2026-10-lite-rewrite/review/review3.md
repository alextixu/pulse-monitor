# Review: review3

The two-process split, the Win32 tray and the runtime knobs are sound for this codebase, but as written the plan will miss at least the memory target and cannot prove any of the five targets. (1) LibreHardwareMonitor keeps a per-sensor value history (ISensor.ValuesTimeWindow, default one day; the shipped 0.9.6 DLL exposes get_/set_ValuesTimeWindow, AppendValue and a TimeSpan.FromDays ref) and nothing in Pulse sets it to zero: at 1 Hz with ~200 sensors that is roughly 3 MB/h of growth, so the resident agent passes 60 MB within a day regardless of everything else in section 9. (2) Neither memory nor threads are costed: adding the spike baseline to LHM/NVAPI/WMI/HidSharp/OpenRGB.NET/pipes plus a gen0 budget that the GC sizes from the 12700K's 25 MB L3 (~12 MB) lands at ~55-65 MB WS and 24-30 threads with the design's own choices (System.Drawing, WMI kept, parallel blocking provider polls, OpenRGB.NET read loop, one HID++ reader thread per stream). (3) The <1 % CPU claim rests on an unmeasured LHM Accept (EC WaitForStatus, SMBus SPD reads, NVML PCIe-throughput calls that block ~20 ms each) buried inside today's 89 ms/tick, and the design carries no instrumentation to find out. Top three fixes: zero LHM's history window and re-measure; add a per-tick stats line and a go/no-go gate on Accept CPU before committing to 1 Hz; handle WM_QUERYENDSESSION/WM_ENDSESSION in the tray window because AppDomain.ProcessExit is not guaranteed for a WinExe on logoff.

## blocker (1)
### LHM per-sensor value history is never disabled and grows ~3 MB/h at 1 Hz
**Detail:** LibreHardwareMonitor's Sensor appends an averaged SensorValue (float + DateTime, 16 B) every 4 updates and keeps them for ISensor.ValuesTimeWindow (default TimeSpan.FromDays(1) since 0.9.2). The shipped publish\win-x64\LibreHardwareMonitorLib.dll 0.9.6 contains get_ValuesTimeWindow/set_ValuesTimeWindow, AppendValue and a TimeSpan.FromDays member ref; `grep ValuesTimeWindow src/` finds nothing in Pulse (LibreHardwareMonitorService.cs:355-398 configures Computer only). With the design's 1 Hz Accept (architecture.md §9) and ~200 sensors on the rig (CPU 20 thread loads + 12 core temps/clocks, NCT6798D ~40, GPU ~25, EC, DIMMs, 3 NVMe) that is 200 × 16 B / 4 s ≈ 0.8 KB/s ≈ 2.9 MB/h, ~69 MB after 24 h (RingCollection doubling can make the peak higher). The <60 MB WS target (§ Targets) is therefore unreachable within a day no matter what else §9 trims; today's 205 MB private was measured only 17 min after start (measure.md) so the baseline hides this.

**Fix:** In LibreHardwareMonitorService after computer.Open() (and in IComputer.HardwareAdded / IHardware.SensorAdded handlers, recursing SubHardware) set sensor.ValuesTimeWindow = TimeSpan.Zero for every sensor; add it to §9; verify with a 15-minute soak that GC.GetGCMemoryInfo().HeapSizeBytes stays flat and add a unit test around the visitor that asserts the window is zero on a fake sensor tree.

## major (8)
### No per-component memory budget; design keeps GDI+ and WMI and ignores the gen0 budget, leaving zero margin under 60 MB
**Detail:** Component estimate (spike REPORT.md as baseline): headless .NET 9 + lean knobs + System.Drawing 36-37 MB WS (pure GDI 27-30 MB); managed code touched for LHM 1.2 MB + DiskInfoToolkit 0.9 + System.Management 0.3 + HidSharp 0.24 + RAMSPDToolkit 0.24 + OpenRGB.NET + STJ + M.E.Logging + Pulse.* ≈ 6-9 MB; nvapi64/nvml images ≈ 4-8 MB; WMI COM stack (wbemprox/wbemcomn/fastprox + RPC) ≈ 3-6 MB — and the LHM DLL shows no WMI class names (SMBIOS via GetSystemFirmwareTable), so the ONLY WMI user is DiskMediaTypes.cs:22 (MSFT_PhysicalDisk once at init); HID/CfgMgr32/Winsock ≈ 2 MB; workstation GC gen0 budget is derived from the largest cache (25 MB L3 on the i7-12700K → ~12 MB min budget after the 5/8 adjustment) so WS carries up to +12 MB of touched gen0 pages between collections even with a tiny live heap. Sum ≈ 55-65 MB before the history bug above; the spike's low numbers come from a process that allocates ~nothing.

**Fix:** Commit to the pure-GDI renderer now (spike run 3: -7 to -9 MB WS, -1 thread, gdiplus not loaded, 1.5 ms/tick); replace DiskMediaTypes' WMI query with IOCTL_STORAGE_QUERY_PROPERTY (StorageDeviceSeekPenaltyProperty / StorageAdapterProperty bus type) so System.Management and the COM stack never load; keep per-tick allocation under ~5 KB (cache SnapshotBuilder FanBinding/DiskMetadata, reuse FanControlSettings/presence snapshots as §9 says) and, if measurement still shows WS > 60 MB, cap gen0 with DOTNET_GCgen0size=0x400000 set by install-pulse.ps1 in the task action (or an agent self-relaunch when the var is missing); put the resulting table in architecture.md with a measured number per row.

### <20 threads is not credible with the design's threading choices
**Detail:** Baseline headless process: 12-13 threads (REPORT.md). Design adds: Pulse.Engine thread (+1); hardware loop (+1, must not be a pool task); HID++ reader threads — HidppTransport.cs:235-244 starts one dedicated Thread per open HidStream (short + long reports) per receiver/device, kept open between polls (+2-3); HidSharp DeviceList.Local device-change thread (HidInterfaceEnumerator.cs:46, AsusRogBatteryProvider.cs:161) (+1); OpenRGB.NET ReadLoop (+1, design keeps the library); WMI/COM RPC workers if System.Management stays (+2-3); NVAPI internal threads (+0-2, unverified); thread-pool workers for the blocking Task.Run fan-out — MonitoringService.cs:317/352 polls all providers in parallel, each blocking up to 20 s, plus FanModeController, OpenRgbController.RunAsync (OpenRgbController.cs:849) and the pipe — peak 4-8 that linger ~20 s. Total ≈ 24-30. Nothing in §3 bounds concurrency; ThreadPool min threads = 20 on this machine so the pool never throttles growth.

**Fix:** Add a thread budget table to §3 and enforce it: poll providers sequentially on one dedicated 'devices' thread (they are sync under the hood, WindowsBluetoothBatteryProvider.cs:39), run LHM Accept/SetFan synchronously on a dedicated hardware Thread, run FanModeController.UpdateAsync on the engine thread (it is already single-flight), drop WMI (see memory item), and log Process.Threads.Count in the stats line; treat >20 after a 24 h soak as a failed target.

### <1 % CPU rests on an unmeasured LHM Accept; §9 does not touch the dominant per-tick work
**Detail:** Today's 89 ms CPU/tick (measure.md) mixes Avalonia binding churn, Skia tray render, telemetry and LHM; the hardware map says the per-group cost is unmeasured (hardware.md openQuestions). §9 only disables Controller/PSU (nothing present on the rig, so ~0 gain), throttles Memory to 5 s and keeps storage at 10 s. What stays at 1 Hz: Intel MSR reads for 20 threads via PawnIO IOCTLs, NCT6798D port I/O, ASUS EC reads through WindowsEmbeddedControllerIO.WaitForStatus (present in the DLL; its wait loop may spin), NVAPI/NVML calls including NvmlDeviceGetPcieThroughput (3 refs in the DLL; the NVML call blocks ~20 ms per direction), SnapshotBuilder's full rebuild (~40 regex matches, 9 FanBinding + 9 FanInfo + 7 TemperatureReading + 3 StorageInfo + DiskMediaTypes.Find per drive per tick, SnapshotBuilder.cs:53-116,340), FanModeController allocations, telemetry row, tray render in the user's CpuLoad mode (content changes almost every second so the 400 ms coalescing saves nothing). 1 % of one core is 10 ms/tick; if Accept alone is 20-40 ms CPU the target is impossible at 1 Hz without changing what LHM reads.

**Fix:** Before implementation, run a 30-line elevated spike (or the agent with a --measure flag) that opens LHM with the same groups and reports Process.TotalProcessorTime delta per 60 Accepts with each group toggled (CPU, GPU, Motherboard with/without EC, Memory, Storage); decide cadence per group from the data (e.g. GPU/CPU 1 s, Super I/O 2 s, EC off, Memory via GlobalMemoryStatusEx) and write the numbers into §9; wrap hardware.Update() in UpdateVisitor with a Stopwatch per Identifier so the stats line (next item) shows where the time goes in production.

### No instrumentation: none of the five targets can be verified after deployment
**Detail:** architecture.md has targets (WS, CPU, threads, tray latency, UI latency) but no measurement points, no stats output and no acceptance script; measure.md shows the only external probe (Get-Process from an unelevated shell) cannot read CPU time or modules of the elevated process, and the 9.9 s pre-Main gap and 89 ms/tick could not be attributed.

**Fix:** Add an EngineStats component: per tick Stopwatch for accept (per hardware node), build, presence+fanmode, csv, ipc serialize/send, tray render+NIM_MODIFY; every 60 ticks log one Information line and publish it over IPC (`Stats` message for the About card): accept avg/max per group, build/fans/csv/ipc/tray avg, Process.TotalProcessorTime delta per wall second, Environment.WorkingSet, PrivateMemorySize64, GC.GetTotalAllocatedBytes delta, GC counts gen0/1/2, GC.GetGCMemoryInfo().HeapSizeBytes, Process.Threads.Count, HandleCount, GetGuiResources(GDI/USER). Startup: log Process.StartTime→Main, →NIM_ADD ok, →'Hardware #1'; UI logs Main→Window.Opened and connect→Hello received. Ship tools/measure-agent.ps1 (elevated) that samples for 10 min and prints pass/fail against the targets; write the measured values back into architecture.md.

### Shutdown list omits logoff/system shutdown (WM_QUERYENDSESSION/WM_ENDSESSION); ProcessExit is not guaranteed for a WinExe
**Detail:** §4 lists clean exit, --quit, unhandled exception and ProcessExit (mirroring Program.cs:73-88, App.axaml.cs:92-106). The agent is a WinExe with a hidden top-level TrayWindow (§7): on logoff/shutdown Windows sends WM_QUERYENDSESSION/WM_ENDSESSION to that window and terminates the process when it returns; AppDomain.ProcessExit is only reliable for console processes (CTRL_SHUTDOWN_EVENT) or Environment.Exit. Consequences: FanModeService.StopApplying → IHardwareMonitor.Dispose does not run (fans left at the last Quiet duty until the next logon recovers them through fan-recovery.json as orphans with the stand-in curve and a 'stuck fans' notice), StateStore's 2 s debounce loses the last lighting/battery changes, settings' 500 ms debounce likewise, telemetry's 5 s buffer is lost.

**Fix:** In TrayWindow.WndProc handle WM_QUERYENDSESSION (return TRUE after calling ShutdownBlockReasonCreate while the shutdown runs) and WM_ENDSESSION (run AgentCore.ShutdownAsync(TimeSpan.FromSeconds(3)) synchronously: fans handed back, stores flushed, OpenRGB child stopped); add this trigger to §4's list and a test on a fake monitor that the dispose order is identical to the --quit path.

### Lighting memory re-applies a device-level intent over later zone colours and can target the wrong duplicate device
**Detail:** §8: 'zone colours are not remembered' and every successful SetDeviceColor/SetAll/SetMode/TurnOff records a device-level intent that is re-applied after each connect / RgbDevicesChanged. Scenario: user sets the motherboard to blue (intent Color), then paints its ARGB header zones individually via LightingView zones (SetZoneColorAsync, LightingViewModel.cs:399-404); on the next reboot the agent re-applies blue to the whole device and erases the zone layout — worse than today, where nothing is re-applied. Separately, Key uses '#2/#3' suffixes in enumeration order for identical devices (rgb.md persistedState; OpenRgbController.cs:1049-1051), e.g. two Kingston Fury sticks, so a detection-order change swaps which stick receives which intent.

**Fix:** Record a Zones dictionary (zone index → colour) in the Lighting intent and clear the device Color when a zone is set (or add Kind=Zones); apply device-level first, then zones; for duplicate Keys either refuse to remember (log once) or require Location/Serial to be present; add StateStore tests for both cases to tests/Pulse.Core.Tests.

### UpdateSettings(whole AppSettings) competes with agent-side mutators and can overwrite the user's fan group lists / hidden devices
**Detail:** §4 has both agent-side mutators (SetFanMode, SetSyncedPercent, SetFanMembership mutate FanGroupExcludedIds/IncludedIds as FanModeService.cs:89-99 does today) and UpdateSettings(AppSettings settings, string? changed) which 'applies' a full copy held by the UI (§6: 'SettingsViewModel mutates that copy'). If the UI's copy is stale when any setter fires (broadcast not yet applied, or an implementation that keeps mutating its own instance because replacing the object under live two-way bindings is awkward), the agent overwrites the lists/HiddenDeviceIds with old values — the user's fan setup, which the memory feature promises to keep, silently reverts.

**Fix:** Make the agent apply only the property named by `changed` (reject/ignore null from the UI, or send a {Name, Value} patch message instead of the whole object); keep whole-object replace only for the sanitiser path; add an IPC round-trip test where a SetFanMembership precedes an UpdateSettings(Theme) with a stale copy and assert the membership survives.

### Tray <2 s and UI <2 s targets have no measurement definition; today's 9.9 s pre-Main gap is unexplained and the UI cold path is borderline
**Detail:** measure.md: process creation 02:43:19.731 → first log line 02:43:29.635 (9.9 s before any Pulse code), tray at +15.5 s. §9's 'tray icon first (<1 s)' can only fix the post-Main 5.6 s; the design offers no hypothesis for the pre-Main gap (task start at logon, Defender scanning the 105 MB folder incl. the 24 MB WinSDK DLL, host probing). UI: Avalonia cold start loads ~30 MB of native/managed images (Avalonia 14 MB, libSkiaSharp 9.4 MB, HarfBuzz 1.8 MB, ANGLE 5.4 MB, Inter 1.9 MB), initialises D3D11/ANGLE and enumerates system fonts (CJK-heavy) on first text — typically 1.5-2.5 s on first launch after boot even with R2R; the pipe connect + Hello (~30-60 KB JSON: 4 devices × ~30 modes + per-LED colours the UI never shows beyond Colors[0], ui.md) adds <50 ms and is not the bottleneck. With UiIdleExitMinutes=5 almost every open is this cold path.

**Fix:** Define both targets from Process.StartTime (not Main) and log the deltas (Main, NIM_ADD, Hardware #1; UI Main, Window.Opened, Hello received); measure the agent through the real scheduled-task launch at logon; shrink the UI cold path by sending Colors[0] only on the wire, dropping Avalonia.Fonts.Inter/ColorPicker as the UI map suggests, showing the window with ui-state.json theme and skeleton values before Hello; revisit the 5-minute idle exit default once numbers exist.

## minor (12)
### System.Drawing vs raw GDI is left open although the spike already answered it
**Detail:** §7 says 'System.Drawing (or raw GDI if the spike shows it is cheaper)'; REPORT.md run 3 shows raw GDI is cheaper on every axis (-7 to -9 MB WS, -1 thread, -20 handles, gdiplus not loaded, half the CPU, -2.47 MB publish) and the spike's ~120-line renderer already reproduces the ring/caps/digits geometry.

**Fix:** Specify raw GDI (CreateDIBSection + analytic AA + DrawTextW + CreateIconIndirect) as the renderer, port TrayIconRenderer's battery glyph to the same pixel routine, and drop the System.Drawing.Common package from Pulse.Agent.

### Tray icon HICON LRU cache contradicts 'previous HICON destroyed after NIM_MODIFY'
**Detail:** §7 specifies both a ≤32-entry HICON cache by content and DestroyIcon of the previous icon after NIM_MODIFY; doing both double-frees cached handles (or leaks if the cache is exempted ad hoc). In the user's CpuLoad mode the value changes nearly every second across 101 values so a 32-entry LRU thrashes; the spike shows a render costs ~1.5 ms and GDI counts stay flat with destroy-after-swap alone (REPORT.md §1, §3 'Icon release').

**Fix:** Drop the cache; render per content change, NIM_MODIFY, DestroyIcon(old); keep only the static fallback icon alive; assert GetGuiResources(GDI) flat in the stats line.

### §3 'hardware loop calls LHM directly' conflicts with §2 'Pulse.Hardware unchanged'
**Detail:** LibreHardwareMonitorService.GetSnapshotAsync and SetFanAsync are Task.Run wrappers around the lock (LibreHardwareMonitorService.cs:111,150); calling them from a loop task still hops threads, and if the loop itself is a pool Task the ~40 ms NVML PCIe wait per tick pins a pool thread.

**Fix:** Add synchronous GetSnapshot()/SetFan() entry points to IHardwareMonitor's implementation (keep the async ones for the UI/demo path) and run the hardware loop on a dedicated Thread named 'Pulse.Hardware'; note the change in §2.

### AgentCore takes OpenRgbServerLauncher, so the UI cannot 'lose every RGB reference' for the in-proc demo client
**Detail:** §4 composition passes OpenRgbServerLauncher (Pulse.Rgb) into AgentCore and exposes OpenRgbBundled; §2 says Pulse.App loses every RGB reference and hosts AgentCore in-process for --demo/--screenshot — both cannot hold.

**Fix:** Introduce IRgbServerLauncher (EnsureRunningAsync, Stop, IsBundled) in Pulse.Core; Pulse.Rgb implements it, the demo uses a null launcher; AgentPaths/OpenRgbBundled come from the interface.

### Agent needs user-facing strings that live in Pulse.App (Strings.cs)
**Detail:** Tooltip format, tray menu labels (開啟/重新整理/以系統管理員身分重新啟動/設定/結束), low-battery balloon title/text (Strings.LowBatteryTitle/LowBatteryToastFormat used at MainViewModel.cs:224), '上次 HH:mm' Detail — all produced in the agent after the split, but Strings.cs is in Pulse.App (Avalonia) and §2 does not move it.

**Fix:** Move Strings.cs (or an AgentStrings subset) to Pulse.Core and bind the UI to it; add the tooltip/menu string tests to the test project as §2 intends.

### UI single-instance objects lack the cross-integrity ACL that SingleInstance uses
**Detail:** §6: Local\Pulse.UI mutex and Local\Pulse.UI.Show event. The UI normally runs elevated (child of the task-launched agent, §5), so these objects get the elevated token's default DACL (Administrators/SYSTEM); a developer's unelevated Pulse.UI.exe then gets UnauthorizedAccessException on both and can neither detect nor signal the running UI. SingleInstance.cs:127-154 already solves this for the agent with Authenticated Users Synchronize|Modify.

**Fix:** Create the UI mutex/event with the same explicit security descriptor (MutexAcl/EventWaitHandleAcl) and treat UnauthorizedAccessException as 'already running' exactly like SingleInstance.cs:43-48.

### Elevation relaunch from the UI banner makes the window vanish and never return
**Detail:** §4 RelaunchElevated is executed by the agent; the agent exits after a successful launch (as App.axaml.cs:138-141) and §6 says 'Agent exit → UI exits', so the UI the user is looking at dies. The new agent starts with the old args (--minimized from the task) and §7 never starts the UI at boot, so nothing reopens it.

**Fix:** Pass --show-ui (or set a flag in state.json) on the relaunch when a UI client was visible, and have UiLauncher honour it after the tray is up; the elevated UI then reconnects to the new pipe.

### LHM Memory group at 5 s still polls DDR5 SPD hubs over SMBus; MemoryInfo itself costs microseconds
**Detail:** §9 throttles the Memory group to 5 s. The LHM DLL has 11 RAMSPDToolkit refs; Pulse only consumes MemoryInfo Used/Total/Load (SnapshotBuilder.cs:292-315) plus DIMM temps in OtherTemperatures, and already filters SPD pseudo-sensors (SnapshotBuilder.cs:143-145). SMBus traffic contends with OpenRGB's SMBus writes to the same Kingston Fury DIMMs (hardware.md wasteFound), and RAMSPDToolkit stays loaded.

**Fix:** Set IsMemoryEnabled=false and build MemoryInfo from GlobalMemoryStatusEx on the hardware thread; keep DIMM temperatures only behind a new opt-in setting (ProbeDimmTemperatures) if the user wants them — see question.

### Persisting FanFirstSight.EverSpun without expiry makes an unplugged header visible forever
**Detail:** §8 seeds FanPresenceTracker from memory; EverSpun is sticky (FanGroupPolicy.cs:91-114) so a header whose fan was later removed keeps Presence=Visible with 0 RPM across every restart, whereas today a restart re-evaluates after 3 samples. The design has no reset rule for FanFirstSight.

**Fix:** Store EverSpun with a LastSpunAt timestamp; when the fan reports RPM 0 for the whole first grace window of a new agent session (or the BootTime changed) drop EverSpun and let the tracker re-decide; keep Percent/Rpm first-sight for the pump heuristic.

### Bounded auto-reconnect relaunches the bundled OpenRGB even when the user's own instance was in charge
**Detail:** §9: after watchdog Error, reconnect at 5 s/15 s/60 s/5 min and 'relaunch bundled copy when UseBundledOpenRgb'. On the live rig the launcher returned AlreadyRunning (measure.md) — the user runs their own OpenRGB. If the user closes it, Pulse starts the headless bundled server and takes the SMBus/USB devices; the next time the user opens the OpenRGB GUI two instances contend (HID devices cannot be opened twice).

**Fix:** Remember the first launch result per agent session: if it was AlreadyRunning, reconnect only (no relaunch) and log once at Information; relaunch only when Pulse started the server itself.

### UI lifecycle details: no immediate frame on SetVisibility(true); --quit cannot guarantee the shared DLL set is free
**Detail:** §5 sends Hardware frames only while Visible, so a re-shown UI displays data up to 1 s stale plus the hidden-period gap; §10 '--quit waits ≤3 s for the UI' then publishes into the same folder — a UI that did not exit (hung Avalonia teardown, elevated vs unelevated mismatch) keeps Pulse.Core.dll etc. locked and dotnet publish fails half-way, leaving a mixed folder.

**Fix:** On SetVisibility(true) push the latest HardwareSnapshot/FanResult immediately; in tools/publish.ps1 verify no Pulse.UI.exe remains (Get-Process) before copying, or publish the UI into a UI\ subfolder with its own DLL set so the agent can be replaced independently.

### Runtime knobs: adopt EventSourceSupport=false too; document the two culture-sensitive sorts that change
**Detail:** §2 lists ConcurrentGC=false, TieredPGO=false, ConserveMemory=3, InvariantGlobalization. Agent-side code has exactly two culture-sensitive operations — MonitoringService.cs:323 StringComparer.CurrentCultureIgnoreCase and WindowsBluetoothBatteryProvider.cs:91 StringComparison.CurrentCultureIgnoreCase — which become ordinal-ignore-case (device order with mixed CJK/Latin names can change slightly); every explicit format is already InvariantCulture and no CultureInfo is constructed, so the knobs are safe. The spike's EventSourceSupport=false is omitted without reason; UseSystemResourceKeys is correctly left off (ex.Message reaches app.log and the UI).

**Fix:** Add EventSourceSupport=false (and MetadataUpdaterSupport=false) to the agent csproj; switch the two sorts to StringComparer.OrdinalIgnoreCase explicitly so behaviour is identical with or without the knob; add a test that CultureInfo.CurrentCulture formatting of the tooltip/telemetry row is byte-identical under invariant mode.

## confirmedSound
- Two processes instead of a lazy in-process UI: Avalonia/Skia/ANGLE images (≈25 MB) and the always-subscribed VMs (ui.md perTickWork) can only leave the resident process by leaving it; the tray spike proves a headless .NET 9 process at 31-41 MB WS with flat GDI counts, working v4 callbacks, balloon, menu and TaskbarCreated handling.
- The CsWinRT drop is real and already mostly done: src/Pulse.Windows targets net9.0-windows and WindowsBluetoothBatteryProvider.cs is the CfgMgr32 implementation (phantom nodes, DN_DEVICE_DISCONNECTED, child GATT battery) — only Pulse.App's net9.0-windows10.0.19041.0 TFM still pulls the 24 MB projection, and the new agent project will not.
- FanPresenceTracker never needs to cross the pipe: FanModeController populates FanModeFanStatus.Presence in every path including the controlAvailable=false branch (FanModeController.cs:159-160, 200-201), so FansViewModel's PresenceOf reads can come from FanModeResult.
- The shutdown order in §4 matches today's contract exactly (FanModeService.StopApplying → MonitoringService → TelemetryLogger → IHardwareMonitor.Dispose → IRgbController → launcher → settings; App.axaml.cs:207-233, Program.cs:73-88), and the --quit protocol/exit codes/Global\ names are preserved.
- Runtime knobs are safe for this codebase: no CultureInfo construction anywhere, all explicit formatting invariant (telemetry, logger timestamps, tooltip), CJK strings are constants unaffected by invariant mode, only two CurrentCultureIgnoreCase sorts degrade to ordinal; ConcurrentGC=false/TieredPGO=false/ConserveMemory have no functional effect on this code; spike measured -3.7 MB WS from the set.
- Hello payload size is not the UI-latency bottleneck: HardwareSnapshot ≈4-6 KB and four RGB devices with modes/zones/LED colours ≈30-60 KB of JSON, well under the 4 MB cap and <50 ms to serialise and parse; STJ source generation handles the record/IReadOnlyList<double?>/IReadOnlyDictionary shapes and polymorphism.
- Keeping OpenRGB.NET for now is the right risk call: the controller-data decoder is the regression risk for a daily-use feature, and the retained cost is one blocked thread plus a 2 s watchdog (OpenRgbController.cs:55,883-903), which is bounded.
- Lighting memory keyed by the controller's stable Key with mode re-resolution by name mirrors the already-proven RgbDefaultsStore/ResolveSavedMode approach (rgb.md persistedState), and re-applying after RgbDevicesChanged covers late-arriving DRAM/GPU controllers.
- A single engine thread draining a Channel<Action> is a faithful replacement for Dispatcher.UIThread: FanPresenceTracker, TemperatureSmoother, Publish and TelemetryLogger's _fanResult all only require single-threaded delivery, not a UI.

## questionsForUser

- UiIdleExitMinutes defaults to 5: for a tray app glanced at every 10-30 minutes almost every open becomes a ~1.5-2.5 s cold start. Accept that, or keep the hidden UI alive longer (≈100-150 MB while hidden) — e.g. 30-60 minutes?
- Drop the LHM Memory group (DIMM SPD temperatures over SMBus, which also contends with OpenRGB on the same DIMMs) and read memory usage from GlobalMemoryStatusEx? This removes the 記憶體 DIMM temperature readings from the System tab's other-temperatures list and from telemetry.

- Should zone colours be part of lighting memory (restored per zone after restart), or is device-level memory enough — in which case the agent must at least not overwrite later zone edits?
- If the memory soak shows the GC's gen0 budget (~12 MB on the 12700K) pushes WS over 60 MB, is it acceptable for install-pulse.ps1 to set DOTNET_GCgen0size in the scheduled task's environment (or for the agent to relaunch itself once with the variable), or must everything stay inside runtimeconfig.json?
