# Review: review2

The two-process split is feasible for the UI layer: the compiled bindings never reach through the service-typed VM properties (grep over Views/*.axaml for Monitoring./Settings./FanModes./Rgb./Elevation./Hardware./AutoStart. is empty), the Pulse.Core models serialise under STJ source generation in .NET 9 as claimed, and the 1 Hz frame is small (~6-7 KB). But §5/§6 are not implementable as written. Top three concerns: (1) the framing is self-contradictory ("message mode" plus "newline-delimited JSON") and the message-mode reading, combined with JsonSerializer.SerializeAsync's 16 KB flush chunking, fragments any payload above 16 KB, which the RgbDevices list (per-LED Colors + 20-40 modes per device) and the proposed Hello (which embeds RgbDevices) exceed on real hardware; (2) the request/reply story has no timeouts, a single 4-deep drop-oldest queue that can discard Replies/Settings/AgentExiting, and three mutually inconsistent rules for what the UI does when the agent goes away (immediate exit, 15 s grace, elevation relaunch), while the VMs' elevation/autostart/path properties are non-notifying getters that would be stale or null if the window is created before Hello as §6 wants; (3) the settings and state ownership has concrete races: AppSettings.Clone() is shallow so the in-proc demo client shares List<string> with the engine, whole-object UpdateSettings loses updates against SetFanMode/SetFanMembership, FansViewModel.Mode echoes the Settings broadcast back as SetFanMode (causing real fan hand-backs), and the demo/screenshot AgentCore has no in-memory StateStore so it pollutes the user's real state.json with demo:* devices. Each has a small, specific fix; none requires rethinking the architecture.

## blocker (1)
### IPC framing is self-contradictory and message mode fragments payloads > 16 KB
**Detail:** §5 says 'message mode, UTF-8 newline-delimited JSON'. These are two different framings: PipeTransmissionMode.Message frames per Write() call, NDJSON frames per '\n'. If message mode is implemented literally: JsonSerializer.SerializeAsync(Stream) flushes to the stream every DefaultBufferSize (16 KB), so one JSON document becomes several pipe messages, and ReadAsync with a buffer smaller than the message returns a partial message (IsMessageComplete=false) that the reader must stitch. Payloads that exceed 16 KB on the user's hardware: RgbDevicesReply / RgbDevices broadcast (RgbDevice.Colors is one object per LED, RgbModels.cs:80 — a keyboard or strip has 100-200 LEDs at ~22 bytes each in object form, plus 20-40 RgbMode records at ~200 bytes per device) and the §4/§5 Hello, which embeds RgbDevices. The 1 Hz Hardware frame (~6-7 KB with 20 cores, 9 fans, 3 drives, ~12 other temperatures, FanModeResult) fits, so the bug only appears when the Lighting tab is opened — exactly the feature the user relies on daily (§1). Separately, nothing says there is a single writer; engine-thread broadcasts and reply tasks writing the same NamedPipeServerStream concurrently interleave bytes.

**Fix:** Pick one framing and state it: PipeTransmissionMode.Byte with a 4-byte little-endian length prefix (reject > 4 MB before allocating), or NDJSON in byte mode (STJ never emits raw newlines when WriteIndented=false). Serialize each message into a pooled ArrayBufferWriter<byte> via Utf8JsonWriter and hand the finished buffer to ONE writer task draining a Channel; read with System.IO.Pipelines (PipeReader) or a length-prefixed loop. Open the pipe with PipeOptions.Asynchronous on both ends so cancellation works. Drop RgbDevices from Hello (send RgbStatus only; the UI already loads devices lazily in LightingViewModel.OnActivated:68-71).

## major (8)
### Outbound 'drop-oldest on a 4-deep queue' can discard Replies, Settings and AgentExiting
**Detail:** §5 applies coalescing/drop-oldest to the outbound queue without restricting it to the Hardware frame. A client that stalls for a few hundred ms (UI thread busy rendering the Lighting tab, GC pause) can have a Reply{Id} dropped, so the awaiting VM command (LightingViewModel.RunAsync:142-159, FanItemViewModel.ApplyAsync:507-531) never completes and IsBusy stays true forever; a dropped Settings broadcast leaves SettingsViewModel/FansViewModel out of step; a dropped AgentExiting leaves the UI running against a dead pipe.

**Fix:** Two outbound lanes: a per-type 'latest only' slot for Hardware, Batteries and Summary (replace, never queue), and a FIFO for everything else that is never dropped. If the FIFO exceeds N messages or the client has not drained for ~5 s, disconnect that client (it reconnects and gets a fresh Hello). Document that Reply and AgentExiting are guaranteed delivery.

### No request timeouts and no rule that the agent's read loop must not await commands inline
**Detail:** §5 says every request gets a Reply but gives no timeout. Real durations: ConnectRgb = OpenRgbServerLauncher.EnsureRunningAsync waits up to 30 s for the SDK port (services map, MonitoringService.cs:175-183) + 2 s connect + optional 30 s detection watch; RefreshNow waits for provider timeouts of 20 s (MonitoringService.cs:55); RgbGetDevices up to 5 s enumerate; every RGB write goes through a serialised gate with 250 ms slices up to 3 s (rgb map). If the agent hangs the UI awaits forever (MainViewModel.RefreshAsync:283-298 keeps IsRefreshing=true; SettingsViewModel.TestConnectionAsync:324-342 keeps IsTesting). Conversely a single short global timeout fails ConnectRgb spuriously. If the IPC reader awaits a command before reading the next message, one slow RGB command blocks SetVisibility/UiHidden/Quit from being read.

**Fix:** Add a per-message timeout table to IpcPulseClient (default 10 s; ConnectRgb 45 s; RefreshNow 30 s; RgbGetDevices 10 s; SetFan 15 s) and surface timeouts as Reply{Ok=false, Error=Strings.*} so the existing Error bindings show them. In IpcServer dispatch each request as its own task (Task.Run or engine Post) and only ever await reads in the read loop; replies go through the single writer.

### Agent-exit / reconnect rules contradict each other and the VMs cannot survive a reconnect
**Detail:** §6 says both 'exits the app if the agent goes away for > 15 s' and 'Agent exit → UI exits'. §4/§7 add a third path: Elevate → agent RelaunchElevated → old agent quits → AgentExiting → by the second rule the UI exits, so the popover the user just clicked in disappears (today the same happens because WindowsElevationService forwards --minimized, but the design does not say which behaviour it wants). If the UI is meant to reconnect: MainViewModel.IsElevated/CanElevate/ShowElevateAction/ElevationBadgeText (:229-233), SystemViewModel.Elevation/IsElevated (:260-262, used at :283), FansViewModel.Elevation (:89, read at :164), SettingsViewModel.AutoStartSupported/CanElevate/SettingsFilePath/LogFilePath/BundledOpenRgbHint/TelemetryPath (:80-88, :240, :288) are plain getters with no PropertyChanged, bound in SettingsView.axaml:49,52,61,124,174,218-219. Compiled bindings read them once, so after reconnecting to an elevated agent the badge still says 一般權限 and the autostart toggle stays disabled. The same staleness hits the §6 plan to open the window 'before the pipe answers': SettingsViewModel.S (:68) is null until Hello, and every getter (SelectedTheme :96, HardwareRefreshSeconds :157 …) throws into the binding engine.

**Fix:** Define AgentExiting{Reason: Quit | Relaunch | Fault}. Quit → UI exits immediately. Relaunch → UI stays, shows StatusText 「正在重新連線…」, retries for 15 s, re-applies the new Hello. Fault (pipe broken without a message) → same 15 s then exit 0. Make the Hello-derived values notifying: a small AgentInfo record (IsElevated, CanElevate, AutoStart, Paths, OpenRgbBundled, Protocol) exposed by IPulseClient with an AgentInfoChanged event; the VMs raise PropertyChanged for the derived getters (or re-raise OnPropertyChanged(string.Empty)) on Hello. Build the VMs only after the first Hello (cold start is dominated by Avalonia init, so the < 1 s warm / < 2 s cold targets are unaffected); keep the ui-state.json theme cache for Application.RequestedThemeVariant only.

### FansViewModel.Mode echoes the Settings broadcast back as SetFanMode and causes real fan hand-backs
**Detail:** FansView.axaml:45-51 binds Mode two-way; FansViewModel.OnModeChanged (:102-106) calls FanModes.SetMode(value) unconditionally, and OnSettingsChanged (:126-136) sets Mode from the settings copy. Today this is safe because FanModeService.SetMode (:73-79) dedups synchronously against the one shared AppSettings object. Over the pipe the dedup compares against the UI's stale copy and the broadcast arrives asynchronously: user clicks 靜音 then 同步 within one round-trip → SetFanMode(Quiet), SetFanMode(Synced) sent; Settings{FanMode=Quiet} arrives → Mode(Synced) != Quiet → Mode=Quiet → OnModeChanged → SetFanMode(Quiet) sent again → Settings{Synced} arrives → Mode=Synced → SetFanMode(Synced)… Every switch runs FanModeController's mode-change branch (FanModeController.cs:174-194), which hands back every held fan via SetFanAsync(null) and logs. The same shape exists for the --screenshot driver (ScreenshotService:229,276 sets fansTab.Mode) through the in-proc client.

**Fix:** Add a _syncingMode guard mirroring _syncingSynced: OnSettingsChanged sets _syncingMode=true around 'Mode = settings.FanMode'; OnModeChanged returns early when _syncingMode. Treat SetFanMode/SetSyncedPercent/SetFanMembership as the only writers of those three fields (never via UpdateSettings), and have the agent dedup against its live settings before touching FanModeController.

### Settings ownership races: shallow AppSettings.Clone() and whole-object UpdateSettings lose updates
**Detail:** AppSettings.Clone() (AppSettings.cs:73) is MemberwiseClone, so HiddenDeviceIds, FanGroupExcludedIds and FanGroupIncludedIds are the SAME List<string> instances in every clone. §6 says 'SettingsViewModel mutates that copy'; in the InProcPulseClient the copy comes from the engine's object, so DevicesViewModel.Hide (:58-62, hidden.Add) and FanModeService.SetMembership-style list edits mutate the engine's live lists from the UI thread while the engine thread reads them in Publish (MonitoringService.cs:432-433) and FanControlSettings.From (FanModeController.cs:23-24). Over the pipe the copy is a deep deserialised one, but §4 UpdateSettings(AppSettings settings, string? changed) replaces the whole object: the UI's SettingsViewModel copy can be stale with respect to fields the agent changed via SetFanMode/SetFanMembership/SetSyncedPercent or its own StartWithSystem reconciliation, so toggling any settings switch rewrites FanMode/lists back to the stale values (lost update).

**Fix:** Make Clone() deep (new List<string>(…)) and have AgentCore always clone on receive. In AgentCore.UpdateSettings apply ONLY the property named by Changed when it is non-null (reflection-free switch on the ~18 names, or a JsonPatch-style UpdateSetting{Name, Value} message); reserve Changed=null for a full replace used nowhere by the UI. Keep SetFanMode/SetSyncedPercent/SetFanMembership as the sole writers for their fields.

### Demo/screenshot AgentCore has no DemoStateStore and will read and write the user's real state.json
**Detail:** §4 names only 'DemoSettingsStore (never writes) and telemetry off' for the in-proc demo AgentCore; §8 makes StateStore write %LOCALAPPDATA%\Pulse\state.json debounced 2 s and on shutdown. DemoBatteryProvider ids are demo:mouse, demo:keyboard, … (DemoBatteryProvider.cs:19-28). Running --screenshot therefore persists nine demo batteries into the real memory; the next real agent start publishes them as IsConnected=false '上次 HH:mm' cards for 30 days (§8 Known devices). In the other direction the user's real remembered devices and LightingMemory intents are injected into the screenshots (docs/screenshots are committed), and LightingMemory would try to re-apply intents against DemoRgbController after each connect.

**Fix:** Add an in-memory IStateStore implementation (DemoStateStore) selected whenever Demo is true, alongside DemoSettingsStore; assert in AgentCore that Demo ⇒ no file-backed StateStore, no TelemetryLogger, no IpcServer, no SingleInstance. Move Demo/* into Pulse.Engine (they only depend on Pulse.Core, verified by the ui map) so the agent's run.ps1 -Demo, the UI's in-proc client and tests share one set.

### RgbDevice.HasDefault goes stale right after 儲存為預設 because the controller never patches its device cache
**Detail:** §5 moves HasDefault onto RgbDevice to kill the synchronous round trip (LightingViewModel.cs:445). The UI's SaveAsDefaultAsync (:424-431) then calls RefreshFromBackendAsync (:433-438) with GetDevicesAsync(refresh:false) and reads Notice = HasDefault ? SavedAsDefault : null (:429) and UpdateRestoreAvailability (:440-458). OpenRgbController.SaveCurrentAsDefaultAsync (OpenRgbController.cs:400-414) writes _defaults.Set(snapshot) but does not call StoreDevice (:757-765), and HasDefault would be computed in Map() only inside RefreshDevicesCoreAsync (:456-465). So refresh:false returns the pre-save array: the 「已儲存為預設」 notice never appears and RestoreTip shows the fallback text until the next full refresh. Same after RestoreDefault/TurnOff for ActiveModeIndex/Colors unless those paths already StoreDevice (they do for colour writes; verify for mode/off/restore).

**Fix:** In SaveCurrentAsDefaultAsync call StoreDevice(device with { HasDefault = true }); in Map() compute HasDefault = _defaults.Contains(key) and Key = keys[i]. Add a Pulse.Core.Tests case: Save → GetDevicesAsync(refresh:false) → HasDefault is true. Alternatively return the updated RgbDevice in the RgbSaveDefault/RgbRestoreDefault/RgbTurnOff replies so the UI never needs the follow-up GetDevices.

### Pulse.Engine would drag Pulse.Rgb (and OpenRGB.NET) back into the UI process, and shared types are not relocated
**Detail:** MonitoringService's constructor takes OpenRgbServerLauncher? and uses OpenRgbLaunchResult and OpenRgbServerLauncher.IsBundled (MonitoringService.cs:63,100,175-179); if it moves to Pulse.Engine unchanged, Engine references Pulse.Rgb, and §2's 'Pulse.App … Loses every hardware/HID/RGB reference' is false (Pulse.App → Engine → Rgb → OpenRGB.NET). Types the design puts on the wire or in the agent but that live in Pulse.App today are not relocated by §2: TraySummary/BatterySummary (MonitoringService.cs:11-46, in §4 Hello), TrayIconContent/TrayTone/TrayGlyphStyle and TrayIconRenderer.Build (TrayIconRenderer.cs:9-30,60-95), TrayService.BuildTooltip (TrayService.cs:102-126) which uses Strings.AppTitle/TooltipDeviceFormat/TooltipCpuFormat/TooltipGpuFormat/Percent/Celsius, the tray menu Strings.Menu* (TrayService.cs:132-156) and LowBatteryTitle/LowBatteryToastFormat for the NIF_INFO balloon — all in Pulse.App.Localization.Strings. LightingViewModel.cs:13,96 uses Pulse.Rgb.OpenRgbInfo.DownloadUrl and SettingsViewModel.cs:240 uses Pulse.Rgb.OpenRgbServerLauncher.IsBundled.

**Fix:** Add IRgbServerLauncher { Task<RgbLaunchResult> EnsureRunningAsync(host, port, ct); bool IsBundled; } to Pulse.Core.Abstractions, implemented by OpenRgbServerLauncher; Engine depends only on Core. Move Strings.cs (no Avalonia dependency, verified) to Pulse.Core/Localization or a tiny Pulse.Strings project referenced by Engine, Agent and App; move TraySummary/BatterySummary and the pure TrayIconContent/Build rules to Pulse.Core (they are the tray/IPC payload). Replace OpenRgbInfo.DownloadUrl in LightingViewModel with the existing Strings.OpenRgbDownloadUrl (currently a dead duplicate) and BundledOpenRgbHint with Hello.OpenRgbBundled (already in §4).

## minor (7)
### IpcJsonContext options and edge cases not specified (NaN, enums, RgbColor shape, discriminator, unknown messages, version mismatch)
**Detail:** Verified: STJ source gen in .NET 9 handles [JsonPolymorphic]/[JsonDerivedType] on an abstract record base, required/init members (UnsafeAccessor-based since .NET 8), IReadOnlyList<double?>, IReadOnlyDictionary<string, FanModeFanStatus> (deserialised as Dictionary), the positional FanModeFanStatus record with its defaulted Error parameter, the mutable AppSettings with List<string>, and readonly record struct RgbColor (structs ignore the positional ctor without [JsonConstructor] and are filled through the init setters, which works). Gaps: (a) STJ throws on NaN/Infinity doubles unless NumberHandling allows named literals — SnapshotBuilder.cs:331 filters NaN today, but FanModeController.cs:218/287 and TelemetryLogger.cs:223 are written as if NaN can occur, so one regression there would kill every Hardware frame; (b) enums-as-strings in source gen needs [JsonSourceGenerationOptions(UseStringEnumConverter = true)]; (c) RgbColor as {"R":..,"G":..,"B":..} is ~22 bytes per LED versus 9 for "#RRGGBB" (and §8 already stores Color as "#RRGGBB"), so a JsonConverter<RgbColor> shrinks the biggest payload 2.5x and unifies both formats; (d) the discriminator is only emitted when serialising as the declared base type (Serialize<IpcMessage>(msg, Ctx.IpcMessage)), not as the concrete type; (e) an unknown 't' from a newer agent throws NotSupportedException and FallBackToBaseType cannot instantiate an abstract base; (f) 'Protocol version 1 in both hellos' says nothing about what either side does on mismatch.

**Fix:** Set JsonSourceGenerationOptions(UseStringEnumConverter = true, DefaultIgnoreCondition = WhenWritingNull, NumberHandling = AllowNamedFloatingPointLiterals, GenerationMode = Metadata | Serialization); add a hex JsonConverter<RgbColor>; serialise through the IpcMessage type info; set IgnoreUnrecognizedTypeDiscriminators = true with a non-abstract UnknownMessage fallback that the reader logs and skips; on Protocol mismatch the UI shows 「Pulse 已更新，請重新開啟」 and exits 0. Add the round-trip test for every message type to tests/Pulse.Core.Tests as §2 promises.

### Theme-follow over the pipe can undo ScreenshotService's direct ApplyTheme and the filter rule is not stated
**Detail:** App.axaml.cs:128-131 re-applies the theme only when Changed is null or 'Theme'. ScreenshotService.cs:233,281 calls App.ApplyTheme directly while fansTab.Mode changes (:229,276) go through the (in-proc) client → AgentCore.UpdateSettings → Settings{Changed=FanMode} broadcast. If the agent ever broadcasts Changed=null (e.g. after its StartWithSystem reconciliation at startup, §4 AutoStart) during a capture, the dark-theme shots flip back to the settings theme mid-run. §6 does not restate the null-or-Theme filter.

**Fix:** State the filter in §6 (apply theme only on Hello and on Settings{Changed is null or "Theme"}); never broadcast Changed=null in steady state (the agent names the field it reconciled); in screenshot mode ignore theme-follow entirely and let ScreenshotService drive Application.RequestedThemeVariant. Apply the user's theme choice optimistically in SelectedTheme's setter rather than waiting for the echo.

### Startup order omits the IPC server and moves the elevation relaunch after the tray icon
**Detail:** §9 lists 'tray icon first, then settings/state, hardware init, providers, RGB connect' — IpcServer is missing, so a tray click in the first seconds launches a UI that spins in its 10 s retry. The services map mustPreserve says the RequestElevationOnStartup relaunch happens before any tray/VM is created (App.axaml.cs:133-144); putting the tray first means an unelevated icon appears, the agent relaunches, a second icon appears and the first disappears, and two Pulse.exe briefly coexist on the Global mutex.

**Fix:** Order: settings load → RequestElevationOnStartup relaunch (exit if a new instance started) → tray icon → IpcServer → state → hardware/providers → RGB. Settings load is a few ms, so the < 1 s icon target holds.

### UI mutex/event in the Local\ namespace needs the same ACL/UnauthorizedAccess handling as SingleInstance
**Detail:** §6 uses Local\Pulse.UI and Local\Pulse.UI.Show. When the agent is elevated its child UI is elevated too (same token, §5), and a dev-launched unelevated Pulse.UI.exe in the same session cannot open those objects (UnauthorizedAccessException) — SingleInstance.cs:43-48 treats that as 'running, signal and exit' but §6 does not say so. Also demo/screenshot runs must skip the guard (Program.cs:34 does today), otherwise --screenshot fails while a normal UI is open.

**Fix:** Reuse SingleInstance's ACL helper (current user FullControl + Authenticated Users Synchronize|Modify) for the UI objects, treat UnauthorizedAccessException as 'another UI is running', and skip the guard entirely when Demo is set.

### Visibility protocol gaps: redundant messages, no immediate frame on show, unused Hello fields, lost debounced writes on exit
**Detail:** §5 has both SetVisibility{Visible} and UiHidden for the same state. After a hidden period SetVisibility(true) does not say the agent sends the latest Hardware frame at once, so SystemView/FansView show data up to 1 s stale (today LatestHardware is always current). Hello carries MemoryState, which no VM reads. With UiIdleExitMinutes=0 ('exit at once') the 300 ms fan slider debounce (FansViewModel.cs:294,345-351) and 250 ms RGB slider debounce (LightingViewModel.cs:255,305-306) can still be pending when the process exits, silently dropping the last write.

**Fix:** Keep only SetVisibility{Visible}; on Visible=true the agent immediately enqueues the latest Hardware+Batteries frames; drop MemoryState from Hello; before idle-exit (and on AgentExiting) fire any armed debounce timers synchronously and await their replies for ≤ 1 s.

### --quit waits ≤ 3 s for the UI with no fallback, so publish can still fail on a locked Pulse.UI.exe
**Detail:** §10: 'Pulse.exe --quit now also tells a running UI to exit (and waits ≤ 3 s) so the publish folder can be replaced'. ## confirmedSound
- Keeping VM public member names is safe: no XAML binding reaches through Monitoring./Settings./FanModes./Rgb./Elevation./Hardware./AutoStart./Options. (grep over src/Pulse.App/Views/*.axaml returned zero hits), so TabViewModelBase.Monitoring/Settings, MainViewModel.Monitoring/SettingsService/Settings, LightingViewModel.Rgb, FansViewModel.Hardware/Elevation/FanModes, SystemViewModel.Elevation and SettingsViewModel.AutoStart/Elevation can be deleted or retyped without touching a view; the only bound service-derived members are the non-notifying getters listed in the reconnect issue.
