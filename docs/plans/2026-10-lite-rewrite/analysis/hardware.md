# hardware

## summary
Pulse.Hardware wraps LibreHardwareMonitorLib 0.9.6 behind Pulse.Core's IHardwareMonitor (src/Pulse.Core/Abstractions/IHardwareMonitor.cs:9-26); all cited paths below are relative to E:\test_think\batterycolorcontrol. LibreHardwareMonitorService (src/Pulse.Hardware/LibreHardwareMonitorService.cs) opens one LHM Computer with CPU/GPU/Motherboard/Controller/Memory/PSU/Storage enabled and Network/Battery disabled (357-369), serialises every LHM call under one lock (_lhmLock, 36), and exposes three operations: InitializeAsync (Task.Run → Open + first Accept + crash-recovery, 83-105/347-429), GetSnapshotAsync (Accept(UpdateVisitor) + SnapshotBuilder.Build, 107-133) and SetFanAsync (SetSoftware/SetDefault + journal write, 135-192), plus a Dispose that restores every touched fan even without the lock after 5 s (198-240). UpdateVisitor refreshes every hardware node per poll but throttles storage to one SMART read per 10 s per drive and never touches rotating disks (src/Pulse.Hardware/UpdateVisitor.cs:14,31,48-60); DiskMediaTypes classifies drives once at init through a WMI MSFT_PhysicalDisk query (src/Pulse.Hardware/DiskMediaTypes.cs:17-43). SnapshotBuilder is a pure mapper from the LHM tree to the HardwareSnapshot record (Cpu/Gpus/Memory/Fans/OtherTemperatures/Storages/Timestamp, src/Pulse.Core/Models/HardwareModels.cs:79-91) and also produces the fan→control bindings used for writes (src/Pulse.Hardware/SnapshotBuilder.cs:53-116). FanRecoveryJournal persists which fans this process holds in manual mode plus "orphaned" fans and the boot time in %LOCALAPPDATA%\Pulse\fan-recovery.json so a crashed/killed Pulse can be recovered on the next start (src/Pulse.Hardware/FanRecoveryJournal.cs). Pulse.Core/FanControl holds the fan-mode state machine: FanModeController.UpdateAsync evaluates one snapshot against FanControlSettings (mode Individual/Auto/Quiet/Synced, include/exclude ids, orphan ids) and issues ordered writes — all hand-backs first, then duty writes — through IHardwareMonitor.SetFanAsync (src/Pulse.Core/FanControl/FanModeController.cs:129-391); QuietFanCurve holds the Board/GPU Quiet profiles, smoothing/hand-off/emergency constants and the orphan stand-in curve (src/Pulse.Core/FanControl/QuietFanCurve.cs); TemperatureSmoother is a time-constant EMA (src/Pulse.Core/FanControl/TemperatureSmoother.cs); FanGroupPolicy/FanPresenceTracker decide pump exclusion and hide unconnected headers (src/Pulse.Core/FanControl/FanGroupPolicy.cs). The working copy carries one uncommitted change: the orphan stand-in runs flat-out only for fans *named* like pumps (FanExclusion.PumpName), no longer for RPM-heuristic PumpLike fans (FanModeController.cs:219-221; committed version used PumpName or PumpLike). Neither Pulse.Hardware nor Pulse.Core references Avalonia, Dispatcher, ObservableObject, CommunityToolkit or Pulse.App (grep over both projects: zero matches; Pulse.Hardware.csproj references only Pulse.Core + LHM + logging/DI abstractions). The cadence is imposed by the App: MonitoringService polls GetSnapshotAsync every 1 s because TelemetryEnabled defaults to true (otherwise HardwareRefreshSeconds=2) and FanModeService runs FanModeController.UpdateAsync after every poll (src/Pulse.App/Services/MonitoringService.cs:274-297, src/Pulse.App/Services/FanModeService.cs:101-138). Measured on the live rig (log 2026-10-21 02:43): "Opening LibreHardwareMonitor" 34.926 → WMI "Disks:" 35.274 → first Accept/"Not reading HDD" 39.172 → "ready" 39.250, i.e. ~4.3 s startup of which ~0.35 s is Pulse's WMI query and ~3.9 s is LHM Computer.Open + first full Update (9 fans, 1 GPU, 7 other temps, 3 drives). Everything in this layer can move into a headless agent essentially unchanged; what must be rewritten is the App-side orchestration (MonitoringService/FanModeService/TelemetryLogger) and the serialisation/localisation boundary.
