# rgb

## summary
Pulse.Rgb is a self-contained class library (no Avalonia reference; csproj deps are only Pulse.Core, OpenRGB.NET 3.1.1, M.E.Logging.Abstractions, M.E.DI.Abstractions — src/Pulse.Rgb/Pulse.Rgb.csproj:9-15) that implements IRgbController on top of the OpenRGB SDK TCP server. OpenRgbController (1130 lines) wraps the synchronous, non-thread-safe OpenRGB.NET client: every operation goes through ExecuteAsync (OpenRgbController.cs:774-841) which takes a single SemaphoreSlim gate, probes the raw socket for a peer close, runs the body, and maps exceptions to status changes; every blocking SDK call goes through RunAsync (:847-880), which runs it on Task.Run and waits in 250 ms slices bounded by a timeout (Connect 2 s, request 3 s, enumerate 5 s; :19-24), re-probing the socket each slice and disposing the client if the call must be abandoned. CONNECT STATE MACHINE (Q1): Disconnected --ConnectAsync--> Connecting (published before the gate, :97-104) --> [new OpenRgbClient autoConnect:false, Connect() under 2 s] --> on failure Disconnected+CannotConnectMessage (:141-147); on success protocol version recorded (:149-150), GetAllControllerData enumerates devices (RefreshDevicesCoreAsync :456-466, captures first-seen defaults), connection failure during enumeration -> Disconnected (:164-170), SDK parse failure -> stay Connected with empty cache (:171-177); then the 2 s watchdog Timer is armed (:179) and Connected+"SDK protocol vN, N devices" published (:180-185). While Connected: watchdog every 2 s does _gate.Wait(0) and OpenRgbClientProbe.IsPeerClosed; a closed peer -> DropClient + State=Error+ConnectionLostMessage (:883-903). Any ExecuteAsync body hitting IOException/SocketException/Timeout/ObjectDisposed/OperationCanceled-from-SDK/ArgumentOutOfRange/IndexOutOfRange (IsConnectionFailure :943-953) -> DropClient + Error (:816-822); SDK rejections (InvalidOperation/Argument/NotSupported) only clear the device cache and set a Message (:823-829). DropClient (:905-923) stops the watchdog, nulls client/devices/rawDevices/deviceKeys and disposes the client (which also unblocks the SDK's internal wait). There is NO automatic reconnect: reconnection only happens when the UI or MonitoringService calls ConnectAsync again (Reconnect button LightingViewModel.cs:76-89, Settings "test connection" SettingsViewModel.cs:331, auto-connect once at Start MonitoringService.cs:140-143). DisconnectAsync (:195-211) and Dispose (:432-452) go to Disconnected. OPENRGB 1.0 FIXES (Q2) live in ApplyModeAsync (:693-723) + OpenRgbModePacket: plain Direct/Custom (per-LED flag, no params) -> client.SetCustomMode; everything else -> hand-built UPDATEMODE (1101) packet written on the library's own socket via reflection with direction forced to 0 for modes without direction flags, speed/brightness clamped into (possibly inverted) ranges, colour mode made consistent with flags; followed by up to 6 GetControllerData read-backs 150 ms apart and an InvalidOperationException ("OpenRGB 沒有套用…") if ActiveModeIndex never matches; TurnOffCoreAsync catches that and falls back to Direct + black (:490-512). OPENRGB.NET CPU BUG (Q3): the library's ReadLoop never sees EOF (ReceiveAllAsync returns on 0 bytes, loop condition is Socket.Connected which only flips after a failed send), so it spins at 100 % CPU and queues garbage until disposed (OpenRgbClientProbe.cs:7-14); Pulse reflects OpenRgbClient._connection._socket and uses Poll(0, SelectRead) && Available==0 twice with a Thread.Yield between as the EOF test (:26-48), run before every operation (:791), every 250 ms slice during a call (:862), and every 2 s by the watchdog (:892). LAUNCHER (Q4): OpenRgbServerLauncher.EnsureRunningAsync first tries a 400 ms TcpClient connect to host:port — anything answering means AlreadyRunning (user's own OpenRGB, never touched); otherwise requires loopback host and <Pulse dir>\OpenRGB\OpenRGB.exe, starts it with "--server --server-port {port} --noautoconnect [AdditionalArguments]" (no window), puts it in a JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE job, and polls the port every 250 ms up to 30 s. The UI (LightingViewModel/RgbDeviceViewModel) consumes only IRgbController + OpenRgbInfo.DownloadUrl + OpenRgbServerLauncher.IsBundled; MonitoringService is the only caller of ConnectAsync/launcher and marshals StatusChanged to the UI thread. The defaults store is a JSON file of first-seen device snapshots keyed by Name|Location|Serial, written atomically; it is the only persisted state owned by this subsystem. There are no unit tests for any of it (no test project in the repo).

## perTickWork
- Connected & idle: only the 2 s watchdog (OpenRgbController.cs:883-903) — _gate.Wait(0), two FieldInfo.GetValue reflections, Socket.Connected, Socket.Poll(0, SelectRead) + Socket.Available (and a second Poll/Available after Thread.Yield only if the first looked closed) (OpenRgbClientProbe.cs:26-48). No allocations beyond boxing-free timer invocation, no logging, no UI update. Effectively zero CPU.
- Connected & idle, library side: OpenRGB.NET's ReadLoop task sits in a blocking/async receive — no CPU while the server is alive; 100 % of one core if the server dies and the probe/watchdog have not yet disposed the client (window ≤ 2 s).
- Disconnected & idle: nothing runs (watchdog period Infinite :55/:907; no reconnect loop).
- Per user action (not periodic): ExecuteAsync does one probe (:791) then the body; a colour change on a Direct-capable device = ReadBack GetControllerData (EnsureModeAsync :678) [+ SetCustomMode + 1-6 GetControllerData read-backs if the mode had to change] + UpdateLeds (:647), each a Task.Run + Task.Delay slice loop; each GetControllerData allocates a full OpenRGB.NET Device (all modes/zones/LEDs/colours), a copy of _rawDevices (:730), a mapped RgbDevice with an RgbColor[] (:733/:981-993) and a copy of _devices (:762). SetAllAsync / TurnOffAllAsync / RestoreAllDefaultsAsync repeat this per device sequentially (:341, :605-624).
- On each GetDevicesAsync(refresh:true) (connect, UI load, detection watcher every 2 s for 30 s after a bundled launch): one GetAllControllerData (:458), ComputeKeys string building per device (:1042-1065), Map of every device, and CaptureMissingDefaults which reads the defaults dictionary per device and writes rgb-defaults.json synchronously inside the gate whenever a never-seen device appears (:464-488, RgbDefaultsStore.cs:71-84, :122-143).
- Logging per connect: ConnectAsync emits 1-2 Information lines (:143 or :151) + MonitoringService logs every status change at Information (MonitoringService.cs:503) and the connect result (:184); Publish() de-duplicates identical statuses (:929). Watchdog disconnect logs one Warning (:894). Nothing logs on a timer while idle.

## mustPreserve
- Direct/Custom switch via SETCUSTOMMODE: when no speed/direction/colours/brightness are requested AND the mode has ModeFlags.HasPerLedColor AND its name is "Direct" or "Custom" (case-insensitive), call client.SetCustomMode(deviceIndex) instead of UPDATEMODE (OpenRgbController.cs:698-705). OpenRGB 1.0 silently drops OpenRGB.NET's UPDATEMODE for these modes (OpenRgbModePacket.cs:9-16, README.md:284-285).
- Hand-built UPDATEMODE (packet id 1101) wire format (OpenRgbModePacket.cs:54-116): 16-byte header `"ORGB"` + uint32 deviceIndex + uint32 1101 + uint32 payloadLength; payload = uint32 totalSize (incl. itself, patched at :114) + int32 modeIndex + uint16 (nameLen+1) + UTF-8 name + 0x00 + uint32 value + uint32 flags + uint32 speedMin + uint32 speedMax + [protocol>=3: uint32 brightnessMin, brightnessMax] + uint32 colorMin + uint32 colorMax + uint32 speed + [protocol>=3: uint32 brightness] + uint32 direction + uint32 colorMode + uint16 colourCount + (R,G,B,0) per colour. Sent fully with a socket.Send loop (:68-69) on the library's own socket obtained via reflection on OpenRgbClient._connection._socket (:23-27, :57); returns false (caller falls back to client.UpdateMode) only when the socket is unreachable (:57-58, OpenRgbController.cs:706-707). Protocol ≤5 clients get no ACK so nothing is read back for this packet (:17).
- Direction rule (OpenRgbModePacket.DirectionFor :32-48): if the mode has none of HasDirectionLR/UD/HV -> send 0; else use the requested direction if valid for the flags, else the mode's current direction if valid, else the first valid one (Left for LR, Up for UD, Horizontal for HV). Speed and brightness are clamped with min/max ordered first because OpenRGB allows inverted ranges (InRange :138-139, used :97-98). Colour mode must match flags: ModeSpecific when colours are given and HasModeSpecificColor, else keep current if consistent with flags, else PerLed > ModeSpecific > Random > None (ColorModeFor :118-136). Colours sent = override, else the mode's current colours, else empty (:101).
- Read-back verification after every mode switch (OpenRgbController.cs:711-722): up to 6 GetControllerData reads 150 ms apart; success when fresh.ActiveModeIndex == modeIndex; otherwise LogWarning and throw InvalidOperationException("OpenRGB 沒有套用「{mode}」模式（伺服器拒絕了這個設定）。") — the UI surfaces this text as the card error. ReadBackAsync also refreshes both caches (:726-735).
- Off fallback (TurnOffCoreAsync :490-512): device has a mode named "Off" (RgbModeRules.IsOff, RgbModels.cs:38) -> ApplyModeAsync(off) and cache Colors = all-black; refused (InvalidOperationException from the read-back) -> SetDeviceColorCoreAsync(black) (Direct + black LEDs); no Off mode at all -> paint black through the normal colour path.
- Colour path (SetDeviceColorCoreAsync :634-670 + ResolveColorMode :740-754): prefer a per-LED mode named Direct, then Custom, then any per-LED mode; EnsureModeAsync first re-reads the device and only switches if the server says a different mode is active (:676-685, cache alone not trusted); then UpdateLeds with LedCount copies. No per-LED mode -> "Static" mode that has HasModeSpecificColor and ≥1 colour, applied via UPDATEMODE with max(1, raw.Colors.Length) copies of the colour (:652-659). Neither -> raw UpdateLeds best effort (:667-669). Zone painting (:228-260) requires a per-LED mode, else paints the whole device; uses UpdateZoneLeds with zone.LedCount colours and updates the cached colours for the zone's LED span (:252-258).
- SetModeAsync parameter rules (:262-335): speed clamped into [min(SpeedMin,SpeedMax), max(...)] only if mode.SupportsSpeed; brightness only if raw.SupportsBrightness (OpenRGB.NET 3.1.1 itself cannot send brightness — only the hand-built packet can, :294-295); colour: per-LED mode -> UpdateLeds after the mode switch (:321-326); mode-specific colour -> exactly raw.Colors.Length copies in UPDATEMODE (:305-311, 'SDK requires exactly as many colours as the mode currently reports'); otherwise the colour is ignored with a debug log.
- Peer-close probe semantics (OpenRgbClientProbe.cs:26-48): reflect _connection/_socket; !socket.Connected -> closed; Poll(0, SelectRead) && Available == 0 means EOF, confirmed by a second identical check after Thread.Yield (an unsolicited packet consumed by the read loop between the calls looks the same); ObjectDisposedException/SocketException -> closed; if reflection fails (field names changed) the probe reports 'not closed' and the request timeouts take over (:12-13, :28). Probe runs before every operation (OpenRgbController.cs:791), each 250 ms wait slice (:862) and every 2 s from the watchdog (:892); a positive drops the client and publishes State=Error with ConnectionLostMessage (:816-821, :894-896).
- Timeout/abandon contract (RunAsync :847-880): SDK calls never run on the caller's thread; on TimeoutException/OperationCanceledException/IOException with the call still running, the client is disposed to unblock the library (its internal wait never returns on its own once the peer is gone) and the faulted task is observed quietly. - Exception taxonomy (ExecuteAsync :774-841, IsConnectionFailure :943-953): only BadIndexException (ArgumentOutOfRangeException subclass for bad device/zone/mode index, :976-977) and the caller's own cancellation propagate to the UI; connection failures (SocketException, IOException, ObjectDisposedException, TimeoutException, OperationCanceledException raised by the SDK's internal token, ArgumentOutOfRange/IndexOutOfRange from the SDK's span readers on a truncated packet, all-connection-failure AggregateException) -> DropClient + Error; InvalidOperation/Argument/NotSupported -> clear _devices cache + status Message '拒絕了這次燈光操作' without disconnecting; anything else -> LogError + generic Message. All methods are safe when disconnected (return fallback, set the '尚未連線' hint only if no message is set, :783-789).
- Connect details: new OpenRgbClient(host, port, "Pulse", autoConnect:false, timeoutMs:1500, protocolVersionNumber:4) (:127-128, MaxProtocolVersion :18, SocketConnectTimeout :20); negotiated protocol stored for packet building (:149-150) and shown as ServerVersion "SDK protocol vN" (:183); enumeration failure that is a connection failure -> disconnect, SDK parse failure -> stay connected with empty cache and retry on refresh (:164-177); 'Connecting' status must be reverted if cancelled before the gate (:110-115). Configure() normalises blank host -> 127.0.0.1 and out-of-range port -> 6742 (:69-82).
- Device identity keys and first-seen capture semantics (:1042-1084, :468-488, RgbDefaultsStore.cs:71-84): Name|Location|Serial (fallback Name|type|LED count), '#n' suffix for duplicates, capture only when the key is absent, snapshot = active mode index+name, IsPerLed, speed (if supported), direction (if supported), colour mode, mode colours and every LED colour as #RRGGBB. SaveCurrentAsDefault re-reads the device first because LED writes do not update the raw list (:405-406).
- Restore resolution order (:514-602): saved snapshot -> mode by name (prefer saved index when names match) -> by index -> firmware effect (first mode that is not Off, not per-LED, not named Direct/Static; RgbModels.cs:40-56) -> NothingToRestore with the exact status messages at :385 and :397. Fit() repeats/truncates saved colours to the current count, null when nothing to fit (:1108-1115); corrupt hex entries are skipped silently (:1088-1105).
- Cache discipline: _rawDevices (OpenRGB.NET Device[]) and _devices (RgbDevice[]) are always replaced together (:459-462) and copy-on-write (StoreDevice :757-765, ReadBackAsync :730-733) so lists already handed to the UI stay immutable snapshots; a mismatch between the two throws StaleCache which nulls _devices (:960-965, :270-275, :516, :696, :729). ForEachDeviceAsync re-resolves each device from the latest cache and skips per-device failures that are not connection failures (:605-624).
- Launcher behaviour (OpenRgbServerLauncher.cs): never stop an OpenRGB Pulse did not start — Stop() only touches _process (:94-116) and EnsureRunningAsync returns AlreadyRunning when anything answers on the port (:63); only launch for loopback hosts ('localhost' or IPAddress.IsLoopback, :143-145) and only if <AppContext.BaseDirectory>\OpenRGB\OpenRGB.exe exists (:45-49); args `--server --server-port {port} --noautoconnect` + optional AdditionalArguments (:120; e.g. --nodetect for tests :54), WorkingDirectory = bundle dir, UseShellExecute=false, CreateNoWindow=true (:123-128); Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE created once and the process assigned via its handle (:167-197; failure only logged at Debug, the process is still stopped on normal exit); port polled every 250 ms up to 30 s, early exit of the child -> Failed with exit code logged (:69-86); Stop kills the entire process tree and waits ≤3 s (:103-104); Dispose closes the job handle (:204-208). The child inherits Pulse's elevation, which OpenRGB needs for SMBus (README.md:300).
- Post-launch detection watcher (MonitoringService.cs:199-225): a freshly launched OpenRGB opens the port before detection finishes, so for 30 s after a Started result the device list is re-read every 2 s and RgbDevicesChanged fires when the count changes (UI reloads cards, LightingViewModel.cs:56). Must be reproduced in the headless agent (and generalised: re-apply remembered state when new devices appear).
- User-facing Traditional Chinese status/error strings in OpenRgbController.cs (:103, :113, :138, :161, :184, :204, :385, :397, :722, :787, :807, :827, :833, :955, :958) and the UI's mapping of RgbStatus.State -> tone/text (LightingViewModel.cs:166-201).

## wasteFound
- OpenRGB.NET's own background ReadLoop task exists for the whole connection lifetime (library internal; evidenced by OpenRgbClientProbe.cs:8-11 and the ReadLoop/ReceiveAllAsync symbols in the 3.1.1 assembly) and burns 100 % of one core between a server exit and the next probe/watchdog tick (≤2 s idle, ≤250 ms during a call). Impact: one extra thread always; brief CPU spike on every OpenRGB exit; the whole watchdog+probe apparatus (OpenRgbController.cs:23,32,55,179,883-923; OpenRgbClientProbe.cs) exists only to contain this. An in-house async client removes all of it.
- Every SDK call costs a Task.Run thread hop plus a Task.Delay-per-250 ms slice loop (OpenRgbController.cs:849-864): per call ≥1 pool thread blocked, 1 Task, 1-12 Timer-backed delays, closures. Only on user actions and connect, so negligible at idle, but it is pure overhead of wrapping a synchronous library.
- Chatty mode switches: ApplyModeAsync always performs 1-6 full GetControllerData read-backs (:713-718) and EnsureModeAsync performs another read-back before deciding (:678); SetDeviceColorAsync on a Direct device = 2-8 round trips instead of 1-2, each allocating a full Device graph (every LED, zone, mode, colour) and a copy of both caches (:730-733, :762). RestoreAllDefaults/TurnOffAll/SetAll do this per device sequentially (:341, :605-624). Estimated 0-900 ms per device per action (README.md:287-288 measured 0-150 ms typical). Could drop the pre-read in EnsureModeAsync when the previous read-back is <1 s old, and read back a single time after 150 ms for modes already confirmed to work on this device.
- WatchDeviceDetectionAsync re-enumerates every device 15 times (every 2 s for 30 s) after a bundled launch (MonitoringService.cs:208-211), each a full GetAllControllerData + ComputeKeys + Map + defaults check (OpenRgbController.cs:456-466), and the UI rebuilds every card on each count change (LightingViewModel.cs:56, 203-232). One-time cost ~15 enumerations; could stop early once two consecutive polls are equal, or use REQUEST_CONTROLLER_COUNT (cheap) and only fetch full data on change.
- Duplicate device state in memory: _rawDevices (OpenRGB.NET Device[] with Color arrays) and _devices (RgbDevice[] with RgbColor arrays) are both retained (:40-41), roughly doubling per-LED storage; small in absolute terms (tens of KB for a few hundred LEDs) but unnecessary with an in-house model.
- Reflection on private fields at every probe (OpenRgbClientProbe.cs:32, two FieldInfo.GetValue calls) and every packet send (OpenRgbModePacket.cs:57): micro-cost, but a maintenance liability pinned to OpenRGB.NET 3.1.1's field names; silent degradation (probe says 'not closed') if the package is ever bumped.
- UI wraps already-asynchronous IRgbController calls in Task.Run (LightingViewModel.cs:108,119,127,135,209,391,402,409,418,427,435,466): an extra thread-pool hop per action with no benefit since ExecuteAsync never blocks the caller beyond the gate wait.
- One DispatcherTimer per device card for slider debounce (LightingViewModel.cs:255,305-306) — N timers alive while the Lighting tab exists; trivial but avoidable with a single shared debounce.
- Blocking shutdown waits: OpenRgbController.Dispose _gate.Wait(3 s) (:438) + OpenRgbServerLauncher.Stop WaitForExit(3000) (:104) → worst case ~6 s of synchronous exit time on the UI thread (App.axaml.cs:224).
- Dead code: OpenRgbInfo.SetupHint (OpenRgbInfo.cs:16-20) is referenced nowhere; RgbStatus.Message carries its own hint text instead (OpenRgbController.cs:958).
- CaptureMissingDefaults performs a synchronous JSON file write inside the connection gate (OpenRgbController.cs:464-488 → RgbDefaultsStore.SaveLocked :122-143) whenever a new device appears during enumeration — during the 30 s detection window this can happen several times; harmless but it serialises disk I/O with RGB traffic.
- Minor correctness smell rather than waste: ConnectAsync's fast path trusts OpenRGB.NET's Connected (:87, :120), which stays true after the server dies (OpenRgbClientProbe.cs:9-10), so a ConnectAsync issued within 2 s of an OpenRGB exit can return true for a dead client until the watchdog fires.

## openQuestions
- (Q8) Re-applying a remembered state such as 'all off except keyboard' IS possible with the current API but needs three additions: (1) a persisted per-device desired state keyed by the stable device Key (not Index); (2) the Key exposed outside OpenRgbController (today private, OpenRgbController.cs:47); (3) an orchestrator step in the agent. Proposed sequence with existing calls: OpenRgbServerLauncher.EnsureRunningAsync(host, port) → IRgbController.Configure(host, port) → ConnectAsync (this already enumerates and captures first-seen defaults, :156, :464) → GetDevicesAsync(refresh:false) → for each device whose Key has a remembered entry: Off → TurnOffAsync(index) (Off mode with read-back, else Direct+black, :490-512); Color → SetDeviceColorAsync(index, color) (Direct/Static path, :634-670); Mode → SetModeAsync(index, modeIndexResolvedByName, color, speed, brightness) (:262-335); Default → RestoreDefaultAsync(index); Untouched (the keyboard) → skip. Then, if the launcher returned Started, keep re-running the same step on every RgbDevicesChanged for 30 s (MonitoringService.cs:203-225) because DRAM/GPU controllers appear late. Mode must be remembered by name and re-resolved like ResolveSavedMode (:589-602) since indices can change. Caveat: devices without an Off mode get Direct+black, which some firmware reverts to its own effect when the SDK client disconnects — so the agent should stay connected (and reconnect) rather than disconnect after applying.
- Should the remembered state be stored in Pulse (new JSON store, proposed above) or delegated to OpenRGB's own persistence? OpenRGB.NET exposes SaveMode(device, mode) (RGBCONTROLLER_SAVEMODE 1102, writes to device flash where supported) and SaveProfile/LoadProfile; OpenRGB also accepts `--profile <name>` at launch. Pulse uses none of these today. Flash saves would make 'keyboard off' survive even without Pulse running, but not every controller supports them and they wear flash; the Pulse-side store is reversible and device-agnostic. The user's '要記憶功能' needs a decision here.
- Does the user want the headless agent to auto-reconnect/relaunch OpenRGB after it exits (currently never happens; reconnect is UI-driven only)? This determines whether the agent needs a back-off loop and how noisy the status logging becomes.
- Replace OpenRGB.NET 3.1.1 with an in-house ~300-line async client (removes the ReadLoop thread, both reflection hacks, the watchdog Timer and the Task.Run slicing) — or keep the library and accept the workaround apparatus? The protocol encoder half already exists in OpenRgbModePacket.BuildPayload; the decoder for REQUEST_CONTROLLER_DATA (protocol 0-4 layouts) is the new work and the main risk (OpenRgbController.cs:947-950 shows the SDK's span readers already throw on truncated packets, so the current code has some tolerance built in).
- Where does the bundled OpenRGB.exe store its own config/log when started by Pulse with WorkingDirectory = bundle dir (OpenRgbServerLauncher.cs:125)? fetch-openrgb.ps1:45-46 strips OpenRGB.json/*.log from the bundle, implying it may write next to the exe (portable mode) or in %APPDATA%\OpenRGB — not verified here; matters for 'what files does the resident agent touch' and for whether an OpenRGB profile could be preloaded.
- Protocol version: Pulse negotiates at most v4 (MaxProtocolVersion = 4, OpenRgbController.cs:18) because OpenRGB.NET 3.1.1 stops there; OpenRGB 1.0 speaks v5 (ACKs for UPDATEMODE, segments). An in-house client could negotiate v5 and use the ACK instead of the 6×150 ms read-back loop — worth confirming against the installed OpenRGB build before relying on it.
- The 'all off' semantics for devices whose only mode is per-LED (no Off mode): today they are painted black in Direct mode; is that acceptable as 'off' for the remembered state, given some devices then show the SDK-held black until OpenRGB is restarted?
- No tests exist for the mode packet, direction rules, key computation or defaults store (no test project in the repo). Any rewrite should first lock these in with unit tests built from the current code (OpenRgbModePacket.BuildPayload is deterministic and easy to golden-test).
