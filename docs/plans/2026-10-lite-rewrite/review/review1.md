# Review: review1

For the memory (記憶) lens the design is directionally right (agent-owned state.json, intents keyed by a stable device Key, intents re-applied after connect, first-seen defaults left alone) but three of its central rules are refuted by the repo's own live data and cannot ship as written. (1) The Lighting memory and rgb-defaults.json are keyed by OpenRgbController.ComputeKeys = Name|Location|Serial, and for HID devices Location is the Windows HID instance path: the live %APPDATA%\Pulse\rgb-defaults.json already contains two "ASUS ROG Falchion (Wireless)" entries whose only difference is the instance segment (8&1b8da785 captured 10-08 vs 8&1ba891e3 captured 10-18). Under the design every re-enumeration of that path drops the remembered intent and, because the agent now turns devices off at every boot, CaptureMissingDefaults will snapshot the black/Off state as the device's "first-seen default", so 還原預設 permanently restores Off. (2) The battery merge rule "a device reported by a provider replaces its memory" is exactly backwards for the user's devices: the live app.log shows "PRO X 2 n/a [Logitech, disconnected]" (20:50:28) after an interface re-open, so the provider's null reading would erase the remembered 82 %; and the Logitech/ASUS flap the design claims to stop is a per-poll IsConnected flip (22:43:00 disconnected → 22:43:30 Discharging) plus the Falchion vanishing between 4-minute endpoint re-opens, which a keep-as-disconnected rule converts into a card greying in and out every poll rather than removing. (3) Demo/--screenshot hosts the same AgentCore in-process but only DemoSettingsStore is made read-only; StateStore would write demo:* batteries and demo lighting into the real state.json and the real agent would then list nine fake devices as 未連線 for 30 days. Beyond those, persisting FanFirstSight freezes pump misclassification and keeps unplugged headers visible forever (regressing the user's "hidden undetected fans" request), UpdateSettings carrying the whole AppSettings loses agent-side mutations, and zone colours "not remembered" leave a stale Off intent that reverses the user's last action. Note: src/Pulse.Logitech/LogitechHidppBatteryProvider.cs changed on disk during this read-only review; Logitech citations below are to HidppInterface.cs/HidppDevice.cs, which did not.

## blocker (2)
### Lighting memory + rgb-defaults keyed by a volatile HID instance path; auto-Off at boot then poisons the first-seen default
**Detail:** §8 Lighting keys intents by RgbDevice.Key = OpenRgbController.BaseKey (src/Pulse.Rgb/OpenRgbController.cs:1055-1063): `{Name}|{Location}|{Serial}` whenever OpenRGB reports a Location. For HID devices Location is the Windows HID path including the per-enumeration instance id. Live proof: \\localhost\C$\Users\alex\AppData\Roaming\Pulse\rgb-defaults.json lines 5 and 85 hold two entries for "ASUS ROG Falchion (Wireless)" differing only in `8&1b8da785&0&0000` (CapturedAt 2026-10-08) vs `8&1ba891e3&0&0000` (2026-10-18); the Z790 key (line 201) embeds the same kind of path. Sequence under the design: boot → agent connects → re-applies Off to the keyboard/mobo → receiver re-plugged or Windows re-enumerates the path → next connect yields a new Key → (a) the remembered intent is orphaned, the user's "all off except keyboard" silently stops; (b) RefreshDevicesCoreAsync → CaptureMissingDefaults (OpenRgbController.cs:456-488, RgbDefaultsStore.AddMissing :71-84, TryAdd only for absent keys) snapshots the CURRENT state — which is now the Off mode / all-black Direct the agent itself applied — as the device's permanent first-seen default, so 還原預設 restores black for ever (README's '回到 Pulse 第一次偵測到裝置時的燈光狀態' becomes false). Today this needs the user to have manually turned the device off right before a re-plug; with automatic re-apply every boot it is the normal state.

**Fix:** Define a normalised identity in Pulse.Rgb and use it for BOTH stores: for `HID:` locations keep only VID_xxxx&PID_xxxx&MI_xx plus the HID serial (strip the `#7&...&0&0000#` instance segment); for I2C keep as is; key = Name|Vendor|Type|normalisedLocation|Serial, '#n' suffix as today. On enumeration, if a key is unknown but exactly one stored entry (defaults or intents) matches Name+Type+LedCount, migrate that entry to the new key instead of capturing. Never capture a first-seen default when the observed state is an Off mode (RgbModeRules.IsOff) or a per-LED mode with all LEDs #000000 while state.json holds an Off/Color intent for that name — log it and leave HasDefault=false (firmware-effect fallback). Add golden tests built from the two live Falchion keys and from the Z790/DRAM/GPU keys.

### Demo / --screenshot in-proc AgentCore writes demo state into the real state.json
**Detail:** §4 Composition: 'Demo mode (UI process): the same AgentCore with Demo providers and a DemoSettingsStore (never writes) and telemetry off' — nothing is said about StateStore, LightingMemory or LowBatteryNotified. DemoBatteryProvider (src/Pulse.App/Demo/DemoBatteryProvider.cs:17-27) emits ids demo:mouse … demo:receiver (incl. an 18 % Low headset and a 7 % Critical stylus), DemoRgbController emits three fake RGB devices, DemoHardwareMonitor emits demo:fan:* ids. With the design's StateStore owned by AgentCore and written on every poll, one `run.ps1 -Demo` or `--screenshot` (used for every README screenshot refresh, commit 1d49fb3) persists nine fake batteries as remembered devices, two LowBatteryNotified ids and demo lighting intents into %LOCALAPPDATA%\Pulse\state.json; the next real agent start publishes them as 未連線 cards for 30 days (§8 'remembered batteries are published immediately'). Today DemoSettingsStore (Demo/DemoPlatformServices.cs:40-56) is the only guard and it only covers settings.json.

**Fix:** Add an IStateStore abstraction with an InMemoryStateStore used whenever AppOptions.Demo is set (same pattern as DemoSettingsStore); state the rule in §4 and §8 ('demo never writes state.json, rgb-defaults.json, fan-recovery.json, telemetry, ui-state.json'). Also require DemoRgbController to populate RgbDevice.Key/HasDefault (§5 only names OpenRgbController) so LightingMemory and the restore button work in screenshots. Add a test: demo AgentCore run → no file under %LOCALAPPDATA%/%APPDATA% Pulse changes.

## major (10)
### Battery merge lets a provider's null/asleep report erase the remembered percent (the exact live PRO X 2 case)
**Detail:** §8 Known devices: 'a device reported by a provider replaces its memory'. Logitech reports asleep devices with IsConnected=false and Status Unknown (src/Pulse.Logitech/HidppInterface.cs:228,239-240) and, after a faulted interface is disposed and re-created, with Percent=null because LastReading starts empty; live app.log line 1104 (2026-10-25 20:50:28) shows 'PRO X 2 n/a [Logitech/UsbReceiver, Unknown, disconnected]'. Bluetooth likewise reports paired-but-disconnected devices with the cached level forever (src/Pulse.Windows/WindowsBluetoothBatteryProvider.cs:73 skips only when Percent is null AND disconnected; the Xbox controller has been 'disconnected 75 %' in every live line). With the replace rule the remembered 82 % becomes 'n/a' at the very moment the feature is supposed to remember it, and 'Detail = 上次 HH:mm' never appears for provider-reported disconnected devices while LastSeenAt would be refreshed by every disconnected report (the Xbox has not connected since 2026-05-28 per the spike's Bluetooth_LastConnectedTime, run1.txt:414).

**Fix:** Merge field-wise, not whole-record: if the provider entry has IsConnected=true → replace and set LastConnectedAt=now; if IsConnected=false → take Name/Kind/Connection/Source from the provider but keep remembered Percent/VoltageMillivolts when the provider's are null, keep Status=Unknown, keep LastConnectedAt, and set Detail to the 上次 text. Store two timestamps: LastConnectedAt (drives the 上次 text, only updated on a connected observation) and LastReportedAt (drives the 30-day expiry). For Bluetooth, seed LastConnectedAt from DEVPKEY_Bluetooth_LastConnectedTime in the CfgMgr32 provider. Test with the two live log shapes (82 % Discharging → n/a disconnected → 82 % Discharging).

### The merge does not stop the user-visible flap; it changes it from appear/disappear to grey-in/grey-out every poll
**Detail:** §8 claims the keep-as-disconnected rule 'stops the list from flapping 2↔3↔4 entries'. Live app.log lines 1438/1441/1445/1447 (22:43:00 → 22:43:30 → 22:45:00 → 22:45:29) show PRO X 2 alternating 'Discharging' ↔ 'Unknown, disconnected' while *reported* every poll (HidppDevice.RefreshAsync marks IsOnline=false on one Hidpp1Error/Timeout, HidppDevice.cs:312-317), and ROG FALCHION present only in the poll right after 'Opened ASUS endpoint' (lines 1440-1441, 1457-1458, ~4 min apart) because the ASUS endpoint is dropped after a failed read and re-opened on a 2-min retry. Under the design the card still toggles 未連線/connected every 30 s–4 min, the tray tooltip/lowest-battery still flip (connected-only), and LogBatteries (MonitoringService.cs:461-474, signature includes IsConnected) still writes a line per flip. The count stabilises; the churn the user sees does not.

**Fix:** Add connection hysteresis to the merge: a device whose provider report flips to disconnected or goes missing stays IsConnected=true with Status=Unknown (card chip 休眠中) until it has been disconnected/missing for ≥ N consecutive polls (N=3, i.e. 90 s at the default cadence) or until LastConnectedAt is older than max(3×BatteryPeriod, 90 s); flip to connected immediately on any connected report. Keep the provider-level fixes (§9 Logitech back-off; hold the ASUS endpoint open between polls instead of 'if cheap'). Add a merge test with the live alternation pattern asserting zero IsConnected transitions.

### Persisting FanFirstSight freezes pump misclassification and keeps unplugged headers visible forever
**Detail:** §8 Fan first sight persists {Percent, Rpm, EverSpun} per fan and seeds FanPresenceTracker so 'decisions are stable across agent restarts'. (a) FanGroupPolicy.LooksLikePumpDuty (src/Pulse.Core/FanControl/FanGroupPolicy.cs:53-54) uses the FIRST sample only: if the previous agent died while fans were at 100 % (orphans exit at 100 %, QuietFanCurve.OrphanExitPercent; Synced 100 % preset) the next start's first sight is ≥95 % / ≥1800 RPM → PumpLike → the fan is excluded from Quiet/Synced. Today that heals on the next restart; persisted it never heals because First is written once (FanGroupPolicy.cs:91-98). (b) EverSpun is sticky (PresenceOf, :109-114); persisted, a header whose fan was unplugged stays Visible with 0 RPM for ever, the telemetry columns keep it, and '沒接風扇的接頭自動隱藏' (README 功能 table, user request 'hidden undetected fans') regresses. (c) Samples is not persisted, so the only effect of the feature on hiding is (b).

**Fix:** Do not persist Percent/Rpm (keep the pump heuristic per session, or persist the minimum RPM/duty ever observed and evaluate against that). Persist EverSpun as LastSpunAt and treat it as 'Visible for a longer grace' only: seeded fans stay Visible for 60 samples without RPM, then become Hidden; drop the entry when LastSpunAt > 7 days. Seed through an explicit FanPresenceTracker.Seed(id, lastSpunAt) API and cover it with tests (fan at 100 % at first sight after a crash must not be PumpLike on the second start; unplugged header hidden after the grace).

### UpdateSettings carries the whole AppSettings: agent-side mutations and quick successive edits are lost
**Detail:** §4/§6: SettingsViewModel mutates a UI copy and calls UpdateSettings(copy, name); the agent 'sanitises, applies live, saves, broadcasts'. The agent also mutates settings itself: FanModeService.SetMode/SetSyncedPercent/SetMembership (src/Pulse.App/Services/FanModeService.cs:73-99 → engine commands in §4), the StartWithSystem reconciliation that today runs in the SettingsViewModel ctor (SettingsViewModel.cs:49-65) and first-run defaults (App.axaml.cs:123-127). A UI copy taken before the agent's broadcast and sent after it overwrites those fields: toggle 納入群組控制 on the Fans tab, switch to Settings and change the theme before the Settings broadcast landed → FanGroupExcludedIds reverted; two slider moves 300 ms apart → broadcast #1 rewinds the slider, then #2 moves it again. Also AppSettings.Clone() is MemberwiseClone (src/Pulse.Core/Models/AppSettings.cs:73): HiddenDeviceIds/FanGroup*Ids lists are shared, so in the InProcPulseClient (demo) DevicesViewModel.Hide mutating 'its copy' mutates the agent's live list off the engine thread.

**Fix:** Replace UpdateSettings{Settings} with UpdateSetting{Name, Value} (JSON value, enums as strings) or specify that the agent copies ONLY the named property from the whole object (Changed=null never accepted from the UI). Add a monotonically increasing Revision to the Settings broadcast; the UI ignores broadcasts older than the last applied and re-applies its pending edit on top. Route every agent-side mutation through the same engine-thread apply/save/broadcast path. Give AppSettings a deep Clone (copy the lists) and use it for the UI copy.

### Zone colours 'not remembered' leaves a stale device intent that reverses the user's last action
**Detail:** §8 Lighting: TurnOff→Off, SetDeviceColor/SetAll→Color, SetMode→Mode, RestoreDefault→Default, 'zone colours are not remembered'. If a device's last recorded intent is Off and the user then paints a zone (SetZoneColorAsync, OpenRgbController.cs:228-260) the entry stays Off; at the next connect the agent turns the device Off, undoing what the user did last. The same hole exists for any command that fails after an earlier success and for SetMode when 'Color' is not recorded (the schema has Color but the prose for Mode lists only name/speed/brightness: Static+red re-applied as Static with the firmware's colour).

**Fix:** Every successful RGB command touches the device's entry: SetZoneColor either records `Zones:{index:'#RRGGBB'}` on a Kind=Zones intent (replayed via RgbSetZoneColor per zone after switching to the per-LED mode) or at minimum removes the device's intent (Kind=Untouched → delete). State explicitly that Mode records Color (when SupportsColor), Speed (when SupportsSpeed) and Brightness (when SupportsBrightness) exactly as LightingViewModel.ApplyModeAsync sends them (LightingViewModel.cs:460-471). Add StateStore tests: Off then SetZoneColor → replay must not turn the device off.

### No way to stop or forget lighting memory from the UI; re-apply fights OpenRGB GUI / vendor software on every reconnect
**Detail:** §8 intents are {Off|Color|Mode|Default} with no 'forget'; RestoreLightingOnStartup is a new settings.json key but §6 adds no control and §11 freezes 'every user-facing string', so it is reachable only by editing JSON. Re-apply runs 'after each successful connect' which, with §9's bounded auto-reconnect, now includes every OpenRGB crash/restart and the user's own OpenRGB being restarted (AlreadyRunning path). A user who changes an effect in the OpenRGB GUI, Armoury Crate or G HUB gets it reverted at the next connect with no in-app explanation or opt-out; a 'Default' intent (RestoreDefault once) re-applies the first-seen snapshot at every boot for ever.

**Fix:** Add a Lighting-tab toggle 「啟動時還原燈光」 bound to RestoreLightingOnStartup and a per-device card menu item 「不要記住這個裝置」 that deletes the intent (Kind=Untouched). Re-apply only once per agent process by default (first successful connect) and expose 'also after reconnect' as part of the same setting (enum Off/AtStartup/EveryConnect). Document the override in README. Minor related: on re-apply suppress RgbStatus.Message publication from RestoreDefault 'NothingToRestore' (OpenRgbController.cs:390-392) so the Lighting status line is not spammed at every boot.

### Late RGB devices never receive their intent; RgbDevicesChanged only exists for 30 s after a bundled launch
**Detail:** §8 re-applies 'after each RgbDevicesChanged'. Today that event fires only from WatchDeviceDetectionAsync (MonitoringService.cs:199-225), which runs only when `ok && launched` (:184), i.e. never on the user's live machine where the log says 'Bundled OpenRGB: AlreadyRunning', and stops after 15×2 s even when launched. DRAM/GPU controllers detected after 30 s, devices added by OpenRGB's 'Rescan Devices', or a keyboard receiver plugged in later keep whatever state they have until the next reconnect. The UI also reloads cards on RgbDevicesChanged (LightingViewModel.cs:56) before the re-apply has run, so cards show pre-apply colours.

**Fix:** Subscribe to OpenRGB's DEVICE_LIST_UPDATED (NET_PACKET_ID 100; OpenRGB.NET 3.1.1 exposes DeviceListUpdated) or poll REQUEST_CONTROLLER_COUNT every 10 s while connected and refresh only when the count changes; make that the single source of RgbDevicesChanged regardless of launch result. Re-apply intents for keys not yet applied in this connection, then raise RgbDevicesChanged again so the UI shows post-apply state.

### Index-based RGB commands over the pipe can hit the wrong device and record the intent under the wrong Key after a reconnect
**Detail:** §4/§5 keep RgbSetDeviceColor/RgbTurnOff/RgbSetMode(int index, …) and §8 records 'the intent per device Key' by mapping index→Key at the agent. Within one OpenRGB instance indices are append-only, but §9 adds bounded auto-reconnect: when OpenRGB restarts with one device not yet detected, indices shift (OpenRGB assigns in detection order, OpenRgbController.cs:1042-1053). A UI card whose 250 ms slider debounce (LightingViewModel.cs:305-306) fires with the stale index, or a RgbTurnOff sent while the agent reconnected, paints a different device and persists Off/Color under that device's Key, which then replays at every boot.

**Fix:** Carry Key in every RGB request (Index only as a hint); the agent resolves Key→current index under the controller gate and answers Reply{Ok=false, Error='裝置已變更，請重新整理'} when the Key is absent. Record intents only from Key-addressed commands. Add an IPC round-trip test with a shifted device list.

### CfgMgr32 Bluetooth provider must reproduce the id format and a correct IsConnected, or memory/hidden/low-battery state misfires on 5-month-old readings
**Detail:** §2 rewrites the Bluetooth provider on CfgMgr32. Ids are `bt:` + BluetoothAddress.ToDisplay (lower-case colon form, src/Pulse.Windows/BluetoothAddress.cs:27-34) and are the keys of HiddenDeviceIds, LowBatteryNotified and state.json Batteries; any format drift resurrects hidden devices and re-notifies. Connection state today comes from System.Devices.Aep.IsConnected; the spike (spikes/bluetooth-cfgmgr32/run1.txt:263,408,470) shows it only as DN status bit 0x02000000 labelled ambiguously 'NEEDS_LOCKING/DEVICE_DISCONNECTED', and the Xbox node reports battery=75 % although Bluetooth_LastConnectedTime is 2026-05-28 (run1.txt:414). If IsConnected is read wrong, the tray 'lowest battery', the NIF_INFO balloon and the merge all act on a reading five months old, and the merge's remembered/provider precedence collapses.

**Fix:** Pin the contract in Pulse.Core tests: id = "bt:" + lower-case aa:bb:cc:dd:ee:ff; IsConnected = present && !(DN status & DN_DEVICE_DISCONNECTED 0x02000000), verified in the spike against the connected Soundbar node (0x0180600A, bit clear) and the disconnected Xbox (0x0380200A, bit set); expose DEVPKEY_Bluetooth_LastConnectedTime as the device's LastConnectedAt; keep the dual-transport Merge rule (WindowsBluetoothBatteryProvider.cs:188-201) and the 'battery value present ⇒ always reported' rule (:73).

### Autostart 'task-aware' is unspecified while the live duplicate launch comes from Run key + task, and the reconciliation code loses its home
**Detail:** §2 says 'autostart becomes task-aware'. measure.md: a second Pulse.exe starts 47–72 s after every boot (7/7) because settings.json has StartWithSystem=true (HKCU Run key, WindowsAutoStartService.cs:60-66) AND the scheduled task 'Pulse' exists. Today the Settings tab reconciles StartWithSystem from the registry at SettingsViewModel construction (SettingsViewModel.cs:49-65); in the design the UI has no IAutoStartService and §4 only exposes AutoStartInfo, so the reconciliation has no owner and the toggle keeps re-creating the Run key next to the task.

**Fix:** Agent-side IAutoStartService: IsEnabled = Run key present || task 'Pulse' exists (schtasks /query or TaskScheduler COM); SetEnabled(true) when the task exists → remove the Run key and return true (no double launch); SetEnabled(false) when the task exists → delete the task (agent is elevated under the task) and the Run key, else Reply error text. Reconcile at agent start, write StartWithSystem, broadcast Settings. Add this to §10 install notes.

## minor (6)

**Detail:** §8 publishes remembered devices with Detail = "上次 HH:mm" from LastSeenAt. For a device not connected since yesterday the card reads e.g. '上次 14:32' with no day; and if LastSeenAt is refreshed by any provider report (asleep/disconnected included) the time means 'last reported', not 'last connected'. **Fix:** Use LastConnectedAt (see merge fix); format '上次 HH:mm' only when today, else '上次 M/d HH:mm'; add the strings to Strings.cs and list them in §11 as the only new strings.

### Low-battery double notification and unreachable reset for Bluetooth
**Detail:** §7: NIF_INFO balloon when no UI is visible, 'the UI still shows its in-window toast when open'. PopoverWindow queues LowBatteryDetected while hidden and flushes on the next show (src/Pulse.App/Views/PopoverWindow.axaml.cs:72-90), so a hidden-but-running UI (UiIdleExitMinutes window) will toast the same event the balloon already showed. §8 reset 'when the device charges' can never trigger for Bluetooth devices (Windows exposes no charge state; WindowsBluetoothBatteryProvider.ToStatus only yields Low/Critical/Unknown), leaving only the ≥5 % rise rule.

### JsonSettingsStore.Sanitize rules for the new keys and for IPC-delivered enums are unspecified
**Detail:** §8 adds UiIdleExitMinutes, RestoreLightingOnStartup, ProbeUsbCoolers; JsonSettingsStore.Sanitize (src/Pulse.App/Services/JsonSettingsStore.cs:92-104) is private static and clamps only the existing numeric fields. **Fix:** Make Sanitize public (design already suggests), add UiIdleExitMinutes clamp 0..1440, and specify that IpcServer catches JsonException per message and answers Reply{Ok=false, Error} without dropping the client. Add sanitiser tests for the new keys.

### HasDefault moves into the RgbDevice payload but nothing pushes a refreshed device after SaveDefault/Restore
**Detail:** §5 replaces IRgbController.HasDefault with RgbDevice.HasDefault; LightingViewModel today re-reads HasDefault synchronously after SaveAsDefault (LightingViewModel.cs:427-429) and RefreshFromBackendAsync re-syncs the card from the cache (:433-438). The design's RgbSaveDefault/RgbRestoreDefault return only Reply{Ok}, so the card's restore button/tip stays stale until some other RgbDevices push.

**Fix:** Have RgbSaveDefault/RgbRestoreDefault/RgbTurnOff/RgbSetMode reply with the updated RgbDevice (RgbDeviceReply{Id, Device}) or raise RgbDevicesChanged with the current list after any state-changing command.

### Elevated relaunch strands the open UI
**Detail:** §4 RelaunchElevated() restarts the agent; §6 'Agent exit → UI exits'; §9 'the UI is never started at boot'. When the user clicks 以系統管理員身分重新啟動 in the popover, the old agent exits, the UI (its child) exits, and the new elevated agent shows nothing — today the relaunched instance at least keeps the tray and the user re-clicks; here the user is left with no feedback that elevation succeeded.

**Fix:** Pass `--show-ui [--tab <name>]` on the elevated relaunch when a UI client was connected; the new agent starts Pulse.UI.exe --popover once the pipe is up.

### Logitech back-off to 15 min makes memory show an in-use mouse as 未連線
**Detail:** §9 replaces the 30 s re-open with exponential back-off 30 s → 1 → 2 → 5 → 15 min per interface. During back-off the interface is not polled, so a mouse that wakes (or G HUB releasing the receiver) is invisible for up to 15 min and the memory layer renders it '未連線 · 上次 …' while the user is moving it.

**Fix:** Cap the back-off at 2 min and reset it on WM_DEVICECHANGE (the agent already owns a Win32 message loop) or when HidInterfaceEnumerator reports a new/changed interface; log one line per state change as planned.

## confirmedSound
- Within one OpenRgbController instance, first-seen defaults are captured before any intent can be re-applied: CaptureMissingDefaults runs inside RefreshDevicesCoreAsync (OpenRgbController.cs:456-466), which ConnectAsync awaits (:156) before returning and which every refresh in the detection watcher runs before RgbDevicesChanged is raised (MonitoringService.cs:211-215). The 'Off before capture' fear only materialises through a Key change, not through ordering.
- Provider-reported paired-but-disconnected devices (Xbox controller via WindowsBluetoothBatteryProvider.cs:73-92; asleep Logitech via HidppInterface.cs:239-240) share the same Id with the remembered entry, so the id-keyed merge cannot produce duplicate cards; ids are stable within a provider (bt:<address>, hidpp:<pairing serial>, asus:<pid>:<serial>).
- HiddenDeviceIds filtering by Id in Publish (MonitoringService.cs:432-434) applies identically to remembered devices, and MainViewModel's low-battery rule skips IsConnected=false (MainViewModel.cs:216), so remembered devices published at start can neither leak past hiding nor trigger a balloon.
- Shipping FanModeResult.Presence over the pipe instead of the tracker matches today's consumers exactly: FansViewModel filters Hidden via presence per fan (FansViewModel.cs:215-219) and TelemetryLogger reads Presence from the result; the tracker itself is single-threaded (FanGroupPolicy.cs:71-74) and belongs on the engine thread.
- Agent ownership of settings.json with sanitise-on-apply reproduces today's single-writer path (SettingsService → JsonSettingsStore.Save → Sanitize) and keeps the UI-side clamps (HardwareRefreshSeconds 1..10, BatteryRefreshSeconds 10..300 in 10 s steps, threshold 5..50) where they are.
- Remembering RGB modes by name and re-resolving to an index at apply time is the right contract: ResolveSavedMode (OpenRgbController.cs:589-602) already proves indices move between OpenRGB versions while names survive.
- LowBatteryNotified reset on charge / ≥5 % rise is an improvement over today's once-per-session set (ui.md wasteFound) and is robust to HID++ BATTERY_STATUS level quantisation (a 20→50→20 bounce is a genuine recharge).
- Keeping DemoSettingsStore read-only is correct and necessary; the design preserves it (only its scope is incomplete, see blocker).
- The 30-day expiry cannot evict Bluetooth paired devices because the provider keeps reporting them with the cached level — consistent with today's behaviour where only un-pairing removes them.
- Device indices within one OpenRGB server instance are append-only during the detection window, so a per-connection 'applied' set keyed by Key is race-free while the watcher adds devices (the problem only appears across reconnects, see issue).
